# gemma4 findings

- [high] Release and family: Gemma 4 was announced 2026-04-02 (Apache 2.0) in E2B, E4B, 26B A4B MoE and 31B dense; the official releases page lists 2026-03-31. MTP drafters followed on 2026-04-16 and the 12B Unified (encoder-free, adds audio) on 2026-06-03. Technical report: arXiv 2607.02770 (July 2026). The HF repo's first public commit ('Preparing for release!') is dated 2026-04-02. At launch the 26B ranked #6 among open models on Arena.
  evidence: https://blog.google/innovation-and-ai/technology/developers-tools/gemma-4/ (2026-04-02); https://ai.google.dev/gemma/docs/releases; https://blog.google/innovation-and-ai/technology/developers-tools/introducing-gemma-4-12b/ (2026-06-03); https://huggingface.co/api/models/google/gemma-4-26B-A4B-it/commits/main; https://arxiv.org/abs/2607.02770
- [high] 26B A4B architecture: 25.2B total / 3.8B active; 30 layers. 25 are sliding-window (window 1024, 8 KV heads x head_dim 256, rope theta 1e4) and 5 are global (every 6th layer, including the last; 2 KV heads x head_dim 512, attention_k_eq_v=true, proportional RoPE theta 1e6 with partial_rotary_factor 0.25). MoE: 128 experts, top-8, moe_intermediate 704, plus a dense shared FFN (intermediate 2112). Other: hidden 2816, 16 query heads, vocab 262144, max_position_embeddings 262144, final_logit_softcapping 30, tied embeddings. The ~550M vision encoder handles image/video (no audio); attention is bidirectional for vision tokens.
  evidence: /run/media/kristian/b39e73c3-74a9-42e9-bffb-28c79f61cc2e/models/gemma4-26b-nvfp4/config.json:20-97; same dir README.md:41-53; https://huggingface.co/google/gemma-4-26B-A4B-it; llama.cpp src/models/gemma4.cpp:4-34,108-113
- [high] Special token ids: <bos>=2, <eos>=1, <|turn>=105, <turn|>=106, <|think|>=98, <|channel>=100, <channel|>=101, <|tool>=46, <tool|>=47, <|tool_call>=48, <tool_call|>=49, <|tool_response>=50, <tool_response|>=51, <|"|>=52, <|image|>=258880, <|audio|>=258881, <|video|>=258884. generation_config eos_token_id=[1,106,50]; config.json eos=[1,106]. 'thought' is a single token (45518); newline is 107.

- [high] Prompt skeleton: [BOS]<|turn>system\n[<|think|>\n]{system text, trimmed}{<|tool>declaration…<tool|>}*<turn|>\n<|turn>user\n{text}<turn|>\n<|turn>model\n. Only messages[0] can be system/developer, and it is merged with the tool declarations. A later system message renders as a literal '<|turn>system' turn, which the model was not trained on. User and system text is trimmed.
  evidence: official template lines 183-236 (copy: /tmp/claude-1000/-home-kristian--------------cforge/3ff4d0f1-90d6-4891-b9a2-ce2beecbc699/scratchpad/g4/official/chat_template.jinja from https://huggingface.co/google/gemma-4-26B-A4B-it/resolve/main/chat_template.jinja); https://ai.google.dev/gemma/docs/core/prompt-formatting-gemma4 (updated 2026-06-03)
- [high] Thinking: <|think|> in the system turn turns it on, and output is <|channel>thought\n…<channel|> followed by the answer. 12B/26B/31B produce 'ghost' thought channels when thinking is off, so the template appends '<|channel>thought\n<channel|>' to the generation prompt. Since July the template also appends '<|channel>thought\n' after tool responses when thinking is on. Google says a 'LOW thinking' system instruction cuts thought tokens by about 20%, and that thinking improves function-calling accuracy.
  evidence: https://ai.google.dev/gemma/docs/capabilities/thinking (2026-06-04); prompt-formatting-gemma4 doc; official template lines 381-389; HF model card Best Practices section 2
- [high] Declaration format: declaration:NAME{description:<|"|>…<|"|>,parameters:{properties:{…},required:[…],type:<|"|>OBJECT<|"|>}}. Properties are sorted with dictsort (case-insensitive in Jinja2) and types are upper-cased. Only description, type, enum (STRING only), items, properties, required and nullable are rendered. anyOf/oneOf/$ref/default/format/min/max are silently dropped; a typeless anyOf renders as type:<|"|><|"|>. The top-level required list keeps input order.
  evidence: official template lines 7-123; Jinja2 render of a test schema (scratchpad render.py, case decl); https://ai.google.dev/gemma/docs/capabilities/text/function-calling-gemma4 example output
- [high] Call and value encoding: <|tool_call>call:NAME{k:v,…}<tool_call|>, with blocks repeated for parallel calls, then the stop token <|tool_response>. Strings are <|"|>raw<|"|> with no escaping: quotes, newlines, braces and backslashes are literal. Numbers and true/false are bare, arrays are [..], nested objects use bare keys. The July template renders null; older templates rendered Python None as 'None'.
  evidence: prompt-formatting-gemma4 doc; function-calling-gemma4 doc (2026-06-04); official template lines 124-155,245-267; local NVIDIA template chat_template.jinja:118-147 (no none branch)
- [high] Tool results go inside the same model turn; no new <|turn> is opened. A string result renders as response:NAME{value:<|"|>…<|"|>}, a mapping as response:NAME{k:v,…} with sorted keys. With role:tool messages, the name is resolved via tool_call_id (falling back to the message name, then 'unknown') and responses are emitted in message order. Since July, image parts become <|image|> right after <tool_response|>. Google recommends dict responses.
  evidence: official template lines 168-181, 277-321; function-calling-gemma4 doc ('For optimal results…' note)
- [high] Reasoning retention: the official rule is to keep thoughts between tool calls inside one model turn and strip earlier turns' thoughts before a new user turn. Templates render reasoning only after the last user message (the April version also required tool_calls). The July template adds preserve_thinking (default false), which keeps tool-call-turn thoughts across user turns. llama.cpp 5e03a1ff4 turns --reasoning-preserve on by default and maps it to preserve_thinking=true, so llama-server keeps these thoughts across user turns by default.
  evidence: prompt-formatting-gemma4 doc 'Managing Thought Context Between Turns'; official template lines 186-187,238-243; local template 238-241; llama.cpp common/arg.cpp:963-967,3756-3768; common/jinja/caps.cpp:22-25; scratchpad render2.py output
- [high] Template bug: if an assistant message has both content (a preamble such as 'Let me look.') and tool_calls, the official template renders the content after the tool responses and closes the turn with <turn|>. In the July version with thinking on, the generation prompt then appends '<|channel>thought\n' without '<|turn>model\n'. llama.cpp only patches prompts that end with '<turn|>\n', i.e. the thinking-off case. The model does write preambles before calls (tech report Table 11 example).
  evidence: scratchpad render of official template (case content_and_call); llama.cpp common/parsers/gemma4.cpp:158-164; https://github.com/ggml-org/llama.cpp/pull/21760 (merged 2026-04-13); arXiv 2607.02770 Table 11
- [high] Template history: 2026-04-02 release; 04-10 'prefix-preserving tool calls' (forward-scan of role:tool messages); 04-28 system-instruction/tool-call handling; 05-18 multimodal tool responses; 07-15 'null handling, reasoning preservation, turn-tag balance, input validation' (string arguments now raise an error); 07-20 response_template added. The HF GGUF metadata for ggml-org, bartowski and google QAT embeds the July template byte-identically; unsloth's variant tolerates string args. The local NVIDIA NVFP4 copy is pre-July. llama.cpp's bundled models/templates/google-gemma-4-31B-it.jinja is the April version.
  evidence: https://huggingface.co/api/models/google/gemma-4-26B-A4B-it/commits/main; HF API ?expand[]=gguf for the 4 GGUF repos (queried 2026-10-29); diff of local chat_template.jinja vs official; llama.cpp git log 3fc65063d (2026-04-10)
- [medium] Argument order follows dictsort, so the model emits keys alphabetically. Raw 26B generations show call:edit{newText:…,oldText:…,path:…} for a tool declared as path/oldText/newText. In one of those samples the model filled oldText with an invented comment after writing newText first.
  evidence: https://github.com/ggml-org/llama.cpp/issues/21799 (2026-04-12; raw generations in comments by am17an and the-phobos); official template line 251
- [high] llama.cpp Gemma 4 handling. Detection: the template contains '<|tool_call>call:'. Parsing: a PEG parser plus a lazy GBNF grammar triggered by the word <|tool_call>; strings are 'until <|"|>', keys match [^:}]+, values are string/dict/array/number/bool/null, tool names are literal. There is no per-tool schema constraint (TODO, gemma4.cpp:260). parallel_tool_calls sets the maximum number of repeats; tool_choice=required makes the grammar non-lazy (fixed 2026-09-19). The parser tolerates repeated <|channel> tokens and a trailing <channel|>. For legacy templates it rewrites role:tool messages into tool_responses and parses tool output that looks like JSON into objects.
  evidence: llama.cpp 5e03a1ff4 common/parsers/gemma4.cpp:3-147,158-301; common/chat.cpp:1212-1221; tests/test-chat.cpp:3003-3250; commits e21cdc11a, ddf03c6d9, f072b1037
- [high] llama.cpp vocab and conversion: <eos>, <turn|> and <|tool_response> are EOG; </s> is demoted to a normal token; add_bos is forced to true and a BOS emitted by the template is stripped. The converter marks channel/tool_call/tool_response/<|"|> tokens USER_DEFINED so they appear in output text, while <|turn>/<turn|>/<|think|> stay CONTROL and are hidden unless --special or preserved_tokens is used.
  evidence: src/llama-vocab.cpp:3049-3051,3145-3166,2786-2791; common/chat.cpp:938-947; conversion/gemma.py:646-656
- [high] Server API. /v1/chat/completions throws 'Cannot use custom grammar constraints with tools.' and cannot continue an assistant message that has tool calls. /completion accepts: prompt as token-id arrays or mixed arrays, return_tokens, grammar/json_schema, grammar_lazy, grammar_triggers {type 0=TOKEN,1=WORD,2=PATTERN,3=PATTERN_FULL; value; token}, preserved_tokens, logit_bias, n_probs, reasoning_budget_tokens/_start_tag/_end_tags/_message and reasoning_control. That covers everything an agent-side renderer plus grammar needs.
  evidence: tools/server/server-common.cpp:1385-1399,1441-1452; tools/server/server-schema.cpp:250-360; tools/server/server-common.h:70-93; common/common.h:146-151; tools/server/README.md:486-500
- [high] GBNF supports token-level terminals <[id]> and negation !<[id]>, and a TOKEN trigger feeds the trigger token into the grammar. Gemma strings can therefore be constrained token-exactly as <[52]> !<[52]>* <[52]>, which is lossless for any content except the delimiter token itself.
  evidence: llama.cpp grammars/README.md:70-89; src/llama-grammar.cpp:1402-1412
- [high] Control-token injection: llama-server tokenizes every prompt (chat or /completion string) with parse_special=true. File or tool text containing '<turn|>', '<|tool_call>', '<|"|>' or '<|think|>' therefore becomes real control tokens. The prompt-parts is_input flag (added 2026-10-14) exists but the server still flattens prompts to one string. HF tokenizers with encode_special_tokens=true (Rust: set_encode_special_tokens) tokenizes such text as ordinary pieces, and /tokenize accepts parse_special=false.
  evidence: tools/server/server-context.cpp:4926; common/chat.h:276-279; tools/server/server-common.cpp (llama_params['prompt']=out_session.prompt().str()); commit ff026f8c0; scratchpad tok.py ('<turn|>' -> id 106 vs pieces with flag); https://docs.rs/tokenizers (0.23.2)
- [high] Key-order mismatch: llama.cpp's Jinja dictsort is always case-sensitive (marked FIXME), while Jinja2 (HF/Google) sorts case-insensitively. Mixed-case property names therefore render in a different order under llama.cpp than in the training format.
  evidence: llama.cpp common/jinja/value.cpp:1346; Jinja2 dictsort default case_sensitive=False; https://github.com/fw-ai/cookbook/blob/main/training/renderer/gemma4.py
- [high] Sliding-window cache reuse: after a prefix mismatch, llama-server resumes only if the mismatch is within about n_ubatch tokens of the cached end or a checkpoint exists before it; otherwise it logs 'forcing full prompt re-processing'. Checkpoints (max 32 per slot, min step 8192) are created at user-message starts and at 4+n_ubatch and 4 tokens before each prompt end. Many related fixes landed in 2026: #21749, #24411 (2026-06-11), #24176, #25472 (2026-07-09).
  evidence: tools/server/server-context.cpp:3787-3899,3983-3996,4094-4180; tools/server/README.md:166-168; https://github.com/ggml-org/llama.cpp/issues/21831 ; /issues/21468 ; /pull/21749; https://llms-explorer.com/tree/llama-cpp-context-checkpoints-and-swa-hybrid-pro/
- [medium] KV memory (f16). Global layers: 5 x (K+V) x 2 heads x 512 x 2 B = 20 KiB/token, i.e. 2.5 GiB at 128K and 5 GiB at 256K. Sliding-window layers: 25 x 8 KiB = 200 KiB/token, but only about n_swa+n_ubatch (1536) cells are kept, about 300 MiB (roughly one checkpoint's size). --swa-full would need about 25 GiB at 128K.

- [high] Google's response_template (tokenizer_config, 2026-07-20) defines the official parse rules. Thinking opens with '<|channel>thought\n' and closes with '<channel|>'.
