# toolcalling-evals findings

- [high] In llama.cpp 5e03a1ff4 tool-call grammars are lazy: they activate only on a trigger (Gemma 4: special token <|tool_call>; gpt-oss: regexes matching ' to=functions' in either the role header or the channel header) and become eager only for tool_choice=required or response_format.
  evidence: /home/kristian/Рабочий стол/llama.cpp/common/parsers/gemma4.cpp:293-301; common/parsers/gpt-oss.cpp:138-149 (commit 5e03a1ff4, 2026-10-16)
- [high] The lazy grammar is suppressed while the model is inside its reasoning block (the reasoning-budget sampler is created whenever a lazy grammar exists and gates it), so 'reason freely, constrain only the call' is built in. Enforcement is rejection sampling (sample unconstrained, validate, mask+resample only if invalid), so overhead is low when the model is already compliant; GPU backend sampling cannot be combined with a grammar.
  evidence: common/sampling.cpp:314-327, 461-473 (grammar_should_apply), 646-690 (grammar-based rejection sampling); assert near line 630
- [high] gpt-oss arguments are JSON-Schema-constrained (p.schema over the tool parameters) and names are restricted to declared tools. Gemma 4 names are restricted but arguments only follow generic gemma4-dict syntax ('TODO: need to extend json-schema-to-grammar'). PR #23247 (schema-constrained Gemma 4 calls) is still OPEN (last update 2026-06-30); testers report its first commit fixes the peg-gemma4 infinite loop, but enum + tool_choice=required returns HTTP 500 and T=0 leaks native call syntax into content.
  evidence: common/parsers/gpt-oss.cpp:104-124; common/parsers/gemma4.cpp:255-266 (TODO at 260); https://github.com/ggml-org/llama.cpp/pull/23247 (gh: state OPEN, updatedAt 2026-06-30; tester comment 2026-05-31)
- [high] /v1/chat/completions cannot carry custom tool-call constraints: 'Cannot use custom grammar constraints with tools'; client grammar_lazy/grammar_triggers/preserved_tokens are erased; user grammar/json_schema are dropped when the session builds a grammar; tool_choice accepts only auto/none/required (no named function); logprobs + tools + stream is rejected. Raw /completion accepts grammar, grammar_lazy, grammar_triggers (types token/word/pattern/pattern_full), preserved_tokens, reasoning_budget_* and prompts as token-ID arrays.
  evidence: tools/server/server-common.cpp:1396-1399, 1460, 1477-1484; common/chat.cpp:314-325; tools/server/server-schema.cpp:252-336; common/common.h:146-157; tools/server/README.md:494-510
- [high] On a final parse failure llama.cpp throws 'The model produced output that does not match the expected <format> format' and the whole turn errors; raw text only goes to the server log, so an OpenAI-API client cannot repair it. In #27720 gpt-oss-20b at T=1.0 produced malformed Harmony channel headers in ~4% of turns: 0/120 failures with reasoning_content round-tripped vs 7/120 when stripped. The maintainer closed it: 'handling garbage output is not feasible from a parsing perspective'.
  evidence: common/chat.cpp:1636-1661; https://github.com/ggml-org/llama.cpp/issues/27720 (comments 2026-08-25/26, closed 2026-08-26); cross-refs show Home Assistant, Hermes, Codex-oss hitting the same failure
- [medium] llguidance in llama.cpp needs a -DLLAMA_LLGUIDANCE=ON build (requires cargo). Grammars starting with %llguidance (Lark syntax) and JSON schemas are routed to it (~50 µs/token mask on a 128k vocab). In common_sampler_init the lazy-trigger path exists only for GBNF, so llguidance can serve eager constraints (e.g., a second-phase args or patch decode) but not the lazy tool-call grammar.
  evidence: docs/llguidance.md; common/sampling.cpp:217-222 (llguidance branch, no triggers) vs 224-273 (GBNF lazy patterns); common/json-schema-to-grammar.cpp:994-1000
- [medium] Constraint-engine performance references: JSONSchemaBench measured llama.cpp GBNF at ~27-30 ms/token vs ~15-16 ms unconstrained (Llama-3.1-8B, A100), Guidance/llguidance at 6-9 ms via fast-forwarding, and Outlines at 3.5-8 s grammar compile. XGrammar-2 adds tag-triggered TagDispatch (the lazy-grammar idea), ~10 ms compile, and reports llguidance at ~250 µs/token on the Harmony format.
  evidence: https://arxiv.org/abs/2501.10868 (Table 2, Jan 2025); https://arxiv.org/abs/2601.04426 (v4 2026-08-05)
- [medium] Quality impact of constraints: the 'Let Me Speak Freely' degradation (2024) was largely a prompt confound (dottxt re-run: GSM8K 0.77→0.78, Last Letter 0.73→0.77 with structure). A 2026 study across 11 open models finds constrained decoding matches or beats unconstrained under identical prompt/format, with validity constraints up to +17.4%. CRANE (ICML 2025), which alternates free reasoning and constrained output, gains up to 10 pts. 'Thinking Before Constraining' constrains only the final extraction and beats CoT on parse success. Implication: constrain after free reasoning and never change the prompt to suit the grammar.
  evidence: https://huggingface.co/papers/2408.02442; https://blog.dottxt.ai/say-what-you-mean.html; https://arxiv.org/html/2610.35328v1 (2026-10-27); https://proceedings.mlr.press/v267/banerjee25a.html; https://arxiv.org/html/2601.07525v2 (2026-05-28)
- [high] Gemma 4 native format: tokens <|tool> 46, <tool|> 47, <|tool_call> 48, <tool_call|> 49, <|tool_response> 50, <tool_response|> 51, <|"|> 52 (string delimiter), <|think|> 98, <|channel> 100, <channel|> 101, <|turn> 105, <turn|> 106. eos = [1, 106, 50], so <|tool_response> is a stop token. Calls look like <|tool_call>call:NAME{key:<|"|>v<|"|>,n:3}<tool_call|>. Strings need no escaping (code and quotes are safe inside <|"|>). Tool results are appended in the assistant turn as tool_responses.
  evidence: local tokenizer.json ids; /run/media/kristian/b39e73c3-74a9-42e9-bffb-28c79f61cc2e/models/gemma4-26b-nvfp4/generation_config.json; tokenizer_config.json (escape_token, response_schema); https://ai.google.dev/gemma/docs/core/prompt-formatting-gemma4 (2026-06-03)
- [high] Gemma 4 thinking rules: <|think|> sits at the top of the system turn (session-level). Thoughts must be kept between tool calls within a turn and stripped before the next user turn. For long-running agents Google recommends summarizing prior thoughts back into context to avoid cyclical reasoning loops. 26B/31B may emit 'ghost' thought channels when thinking is off, so the template appends an empty <|channel>thought\n<channel|>. Google: internal reasoning 'significantly enhances its function-calling accuracy'.
  evidence: https://ai.google.dev/gemma/docs/core/prompt-formatting-gemma4; https://ai.google.dev/gemma/docs/capabilities/thinking; https://ai.google.dev/gemma/docs/capabilities/text/function-calling-gemma4; local chat_template.jinja:179-185, 237-241, 347-353
- [high] For Gemma, llama.cpp converts role:tool messages into an assistant tool_responses field and tries json.parse on string tool content. A tool output that happens to be valid JSON is therefore re-rendered as a key-sorted Gemma dict, while a plain string becomes response:NAME{value:<|"|>…<|"|>}. Tool calls are re-rendered with dictsort'ed argument keys.
  evidence: common/parsers/gemma4.cpp:15-147 (json parse at 56-64); local gemma chat_template.jinja:160-173 (response block), 247-253 (dictsort of arguments)
- [high] Known Gemma 4 + llama.cpp tool-call failure modes: (1) deep nested object args come out garbled; the maintainer says complex object schemas are problematic and recommends a JSON-string parameter (#21680). (2) Array args containing { } get serialized as strings (#21384). (3) 26B edge cases fixed in #21760: missing generation prompt after content+tool call, trailing <channel|>, repeated <|channel>. (4) Content is truncated at a literal <|tool_call> (#22371). (5) Tool calls arrive as content when thinking traces are not sent back; the maintainer says reasoning_content must be returned (#22786).
  evidence: https://github.com/ggml-org/llama.cpp/issues/21680 (2026-04-09); /issues/21384; /pull/21760; /issues/22371; /issues/22786 (2026-05-07)
- [high] gpt-oss / Harmony specifics: tools are defined as a TypeScript namespace in the developer message; calls go to the commentary channel with to=functions.NAME (in the role or channel header) and an optional <|constrain|>json. Stop tokens are <|call|> 200012 and <|return|> 200002 (eos [200002,199999,200012]). CoT must be passed back between tool calls and dropped after a final message, and <|return|> is stored as <|end|>. The template renders only tool_calls[0] (no parallel calls), puts 'Reasoning: <effort>' and 'Current date' in the first system message, and degrades nested schemas (arrays of objects >50 chars become any[]). The model sometimes emits a stray '<|channel|>commentary' prefix.
  evidence: https://cookbook.openai.com/articles/openai-harmony; local gpt-oss-20b-bf16/generation_config.json; chat_template.jinja:10-106, 196-223 (202 date, 203-206 effort), 277-300, 322; common/parsers/gpt-oss.cpp:7-17, 75-77
- [medium] The gpt-oss template differs by source. OpenAI's HF template JSON-encodes tool outputs (message.content|tojson) and arguments. The template embedded in the local Unsloth GGUF ('Chat template fixes by Unsloth', 17,221 chars) renders string tool outputs raw (as the Harmony spec does) and adds a branch that renders message.content in the ANALYSIS channel for non-final assistant messages carrying 'thinking'. llama.cpp maps every reasoning_content to 'thinking', so round-tripping reasoning on final-answer turns likely mis-renders earlier answers as CoT.

- [medium] Tool presentation guidance. Tool-use examples raised complex-parameter accuracy from 72% to 90% (Anthropic internal; 1-5 realistic examples per tool, only where the schema is ambiguous). Manus warns that uniform, repetitive context makes agents imitate past actions (few-shot ruts).

- [medium] Manus context-engineering rules for KV-friendly agents: KV-cache hit rate is 'the single most important metric' (input:output ~100:1). - [high] llama.cpp cannot roll back SWA or hybrid memory to an arbitrary position. On a prefix mismatch the server restores the newest context checkpoint before the divergence, else logs 'forcing full prompt re-processing'. Checkpoints (default 32/slot, min spacing 8192 tokens; --ctx-checkpoints, --checkpoint-min-step) are created at user-message starts (found via per-model message delimiters), at the last user message, and 4+n_ubatch and 4 tokens before each prompt end. The oldest is evicted first. Both reference models are SWA: gpt-oss window 128 on 12/24 layers; Gemma 4 window 1024 on 25/30 layers (full attention at layers 5,11,17,23,29).

- [medium] KV sizes derived from configs (to be confirmed in llama.cpp load logs). gpt-oss-20b full-attention KV ≈ 24 KiB/token at f16 (12×8×64×2×2B), ~3 GiB at 128k; --swa-full adds about the same again, which is affordable next to 12-13 GiB of weights. - [high] Prefix killers in these templates. Session-level flags sit at the very top (gpt-oss 'Reasoning:' effort and 'Current date', Gemma <|think|>), so toggling them per turn re-prefills everything. gpt-oss drops tool-call CoT once a later final message exists, and Gemma renders thoughts only after the last user message, so each new user turn diverges at the first tool-call message of the previous turn. Re-rendered tool calls may also differ from the generated bytes (llama.cpp re-serializes string args into objects; Gemma dictsorts keys), as can re-tokenized text at message boundaries.

- [medium] Measurement noise is large. Anthropic found Terminal-Bench 2 infra errors falling from 5.8% (strict resource caps) to 0.5% (uncapped) and the score rising +6 pts at uncapped, and recommends a per-task resource floor and ceiling. On OpenRouter the same Gemma 4 26B scored 57.3%-68.2% on τ²-airline depending on provider (secondary mirror), so the serving stack alone moves results by ~10 pts.
  evidence: https://www.anthropic.com/engineering/infrastructure-noise (2026-02-05); https://tensortrace.net/models/google/gemma-4-26b-a4b-it-20260403 (OpenRouter data, snapshot 2026-10-24)
