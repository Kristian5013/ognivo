# critique: gui-product

## Overall
Стек выбран верно. Electron 45, React 19, CodeMirror 6 и xterm.js 6 — это то же, на чём в 2026 работают ChatGPT/Codex desktop, Claude Desktop и T3 Code, да и сам Cursor написан на Electron. Monaco нужен только если владелец выберет editor-first IDE, и даже тогда CM6 справится: @codemirror/lsp-client и @marimo-team/codemirror-ai (Apache-2.0) уже дают Cmd-K inline edit и UI для next-edit. В стек стоит добавить @pierre/diffs для ревью, Streamdown с rehype-harden, react-virtuoso и cmdk.

Слабое место черновика — продуктовые решения, а не стек:
- «Уровень Cursor» никак не определён.
- MVP из 13 пунктов идёт параллельно с самыми рискованными этапами M2–M3.
- GUI скопирован с продукта, который рассчитан на сильные облачные модели.

Что такое Cursor на конец октября 2026 (Cursor 3 и 3.27). Это прежде всего Agents Window:
- сайдбар сразу по нескольким репозиториям;
- параллельные агенты: локальные, в worktree, облачные;
- вкладка Changes с переходом к commit и PR;
- просмотр файлов с LSP;
- встроенный браузер с responsive-режимом и Annotate;
- Restore Checkpoint, queue/steer, формы MCP elicitation, голос.
Классическая IDE с Tab стала вторичным режимом.

Что из этого реально на одной 24 ГБ GPU. Почти всё, кроме облачного «флота», но с оговорками:
- Параллельность — один активный и один фоновый агент (-np 2 --kv-unified).
- Tab — только отдельной моделью на 0.5–1.5B. У gpt-oss-20b и Gemma 4 нет FIM-токенов (я проверил их tokenizer.json), поэтому /infill отказывает. По VRAM такая модель помещается (1–2 ГБ), но конкурирует с агентом за вычисления.
- Визуальный Design Mode возможен только с Gemma 4 и mmproj: это около +1 ГБ и потеря переиспользования кеша. Annotate (выбрать элемент DOM и отправить в чат) работает и с чисто текстовыми моделями.

Чем продукт должен отличаться. Двумя вещами, которых нет ни у кого:
1. Интерфейс, рассчитанный на постоянный контроль слабых моделей: @-контекст, утверждение плана, queue/steer, кнопка Continue, rewind/fork, комментарии к diff.
2. Прозрачность локального рантайма: прогресс prefill с причиной промаха кеша, цена действия до клика, VRAM по процессам, «теплота» сессий, кнопка «Ответить сейчас», Inspector токенов. Все нужные поля llama-server на 5e03a1ff4 уже отдаёт.

Рекомендуемый порядок работ:
1. С M1 — ежедневная работа через ACP в Zed и в T3 Code (MIT, Electron+React, режим «Local ACP command»).
2. Затем — заморозить протокол и сделать вертикальный срез GUI на записанных кассетах.
3. Полный MVP — после M3.

Обязательно исправить две вещи:
- Транспорт. WebSocket поверх UDS недоступен ни из renderer, ни из вкладки браузера. Локальный WS без проверки Origin и Host открыт для CSWSH, а за ним стоит демон с shell.
- Политику рендеринга недоверенного контента.

До старта GUI владелец должен решить пять вопросов:
- agent-first или editor-first;
- подтвердить TS-GUI вопреки прежнему принципу pure Rust;
- политику GPU;
- только локально или с удалённым доступом;
- автономию по умолчанию.

## Problems

  - why: В 2026 Cursor — это прежде всего Agents Window (Cursor 3 от 02.04.2026, сейчас 3.27): сайдбар по репозиториям, параллельные агенты, Changes → commit/PR, файлы с LSP, браузер, Restore Checkpoint, queue/steer. IDE с Tab — вторичный режим. Без явного выбора scope расползётся: по оценке gui-tech это 8–12 недель на MVP плюс 6–9 месяцев до v1. Владелец один и будет одновременно ревьюить GUI и самые рискованные Native-адаптеры Harmony и Gemma. Изменения item-модели в M2–M3 заденут GUI дважды: каналы analysis/commentary, токен-спаны, repair-события.
  - fix: Записать решение: v1 — agent-first workbench (класс Cursor Agents Window / Codex app / T3 Code) с лёгким просмотром кода; Tab и полноценная правка с LSP — v1.x. Составить таблицу фич v1 / v1.x / никогда. Зафиксировать измеримые бюджеты «уровня Cursor» и проверять их перф-тестами в Playwright: стрим 60 fps на треде из 10k элементов; задержка ввода меньше 16 мс; открытие файла меньше 100 мс; виртуализованный diff на 5k строк; холодный старт меньше 2 с. Порядок работ: (1) M1 — ACP-адаптер, ежедневная работа через Zed и T3 Code; (2) конец M1 — заморозить item-модель с golden-транскриптами и за 2–3 недели сделать вертикальный срез GUI на кассетах T1, без GPU; (3) M2–M3 — в GUI только багфиксы; (4) M4 — MVP, построенный вокруг контроля (п. 2).
- **[major] Интерфейс рассчитан на сильные автономные модели, как у Cursor. Нет инструментов дешёвого контроля, без которых gpt-oss-20b и Gemma 4 не обойдутся.**

- gpt-oss без high effort резко слабее: SWE-V 37,4 против 60,7.
- Рабочий контекст 64–96K, поэтому явный выбор контекста пользователем полезнее агентного поиска.

- **[major] Из локальных реалий в GUI заложен только метр контекста, кеша и prefill. Нет:

llama-server уже отдаёт всё нужное:

В GUI:

Тайминги и сэмплы прогресса писать в журнал событий: по ним считаются ETA.
- **[major] Нет плана слотов и планировщика GPU для GUI-фич, которые шлют побочные запросы в ту же модель: inline edit, заголовки сессий, commit-сообщения, компакция, фоновые агенты.**
  - why: При -np 1 любой запрос с другим префиксом вытесняет KV основной сессии. Спасает только --cache-ram: по умолчанию 8192 MiB, состояние сохраняется в RAM при потере больше 50% контекста (server-context.cpp:1759–1796). Цена — копирование гигабайт и сериализация запросов. Gemma 4 не может дёшево откатываться: --swa-full на 128K стоит около +25 ГиБ. Скрытые LLM-вызовы в духе Cursor (заголовки, саммари) будут регулярно ломать кеш и останавливать агента посреди хода.
  - fix: Пресет: -np 2 --kv-unified с --kv-unified-per-slot как потолком для побочного слота (например, 16K) и --cache-ram 16–24 GiB (с учётом page cache GGUF и памяти LSP). Явный id_slot: слот 0 — основной агент, слот 1 — интерактивные запросы и фон. В agentd — планировщик с приоритетами: основной агент > интерактивные запросы > фоновые агенты > служебные задачи. Фоновые агенты ставятся на паузу между шагами, пока работает основной. В v1 никаких скрытых LLM-вызовов: заголовок — первая реплика, commit-сообщение — по кнопке и только при свободной GPU. Очередь показывать в строке состояния.
- **[major] Риск «места под FIM и эмбеддинги на GPU почти нет» сформулирован неверно. Tab упирается не в VRAM, а в отсутствие FIM у эталонных моделей и в конкуренцию за вычисления.**
  - why: В tokenizer.json обеих моделей нет FIM-спецтокенов: проверено в /run/media/kristian/b39e73c3-74a9-42e9-bffb-28c79f61cc2e/models/{gemma4-26b-nvfp4,gpt-oss-20b-bf16}. Поэтому /infill отвечает «Infill is not supported by this model» (server-context.cpp:5469).

Открытые next-edit модели при этом маленькие:
- Sweep Next-Edit 0.5B (Q8_0, 531 МБ) и 1.5B: Apache-2.0, GGUF, контекст 8K;
- Zeta 2.1 8B (Q4_K_M, 4,8 ГБ);
- Mellum2-12B-A2.5B — поддерживается в llama.cpp с 06.2026;

Оценка VRAM (не замер):

Реальное ограничение — CUDA time-slicing между процессами: задержка Tab во время prefill агента не измерена.
  - fix: Исправить формулировку риска. Tab — опциональная фича v1.x:
- отдельный llama-server с моделью 0.5–1.5B;
- резерв под Tab в калькуляторе VRAM;
- отмена по нажатию клавиши, короткий n_predict;

- **[major] Транспорт «WebSocket поверх Unix-сокета + токен» недоступен из sandboxed renderer Electron и из вкладки браузера, хотя режим во вкладке заявлен. Вариант из mcp-acp — loopback TCP с отклонением запросов, у которых есть Origin, — делает браузерный режим вообще невозможным.**
  - why: WebSocket в Chromium умеет только ws/wss к host:port, а Node в renderer отключён (sandbox + contextIsolation). Локальный WS-сервер без строгой проверки Origin и Host уязвим для cross-site WebSocket hijacking и DNS rebinding с любой открытой веб-страницы. За ним стоит демон, который исполняет shell-команды от имени пользователя.
  - fix: В Electron: renderer ⇄ main через MessageChannelMain, main ⇄ agentd по UDS с проверкой UID через SO_PEERCRED. TCP-слушатель по умолчанию выключен. Браузерный или удалённый режим — опция:
- agentd сам отдаёт UI на 127.0.0.1:<случайный порт>, тот же origin;
- одноразовый токен во фрагменте URL, страница обменивает его на cookie HttpOnly, SameSite=Strict;
- строгий allowlist для Host и Origin;
- удалённо — только через ssh -L.
Окончательно решить вместе с вопросом владельца про удалённый доступ.
- **[major] Нет политики безопасности для рендеринга недоверенного контента в GUI.**
