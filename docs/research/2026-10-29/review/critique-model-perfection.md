# critique: model-perfection

## Overall
Направление верное и единственно совместимое с целью «идеально под архитектуру»: агент сам владеет форматом на уровне токенов, llama-server работает как токен-движок через /completion, Generic остаётся базовой линией. Но черновик опирается на четыре инварианта, которых закреплённый llama-server 5e03a1ff4 на деле не даёт (проверено по коду):
(1) Безопасная токенизация контента средствами llama.cpp невозможна. Структурные токены обеих моделей имеют тип USER_DEFINED и распознаются даже при parse_special=false. Значит, рекомендация из исследования «/tokenize с parse_special:false» небезопасна.
(2) Потоковый /completion теряет ID токенов, на которых UTF-8 остаётся неполным. Для gpt-oss это эмодзи и псевдографика. Финальный чанк в режиме stream токенов не несёт. Исправление — PR #31244, на 27.10 ещё открыт.
(3) Серверный бюджет мышления и подавление ленивой грамматики внутри мысли не видят префилл '<|channel>thought\n'. Июльский шаблон Gemma вставляет его в каждом tool-шаге, поэтому бюджет срабатывает только на первом шаге хода.
(4) На raw-пути SWA-чекпоинты создаются только у конца промпта.
Плюс дыры по моей линзе:
- компакция только на границах ходов не работает для длинной задачи (у Gemma весь tool-цикл живёт внутри одного turn);
- MCP через вложенный mcp_call — это слабое место обеих моделей;
- формы инструментов нарушают правила Gemma (update_plan — массив объектов);
- не задано размещение для gpt-oss (system-namespaces дали 60.4% на SWE-V);
- нет правил, куда класть динамический контекст, нет семантики параллельных вызовов Gemma, нет топологии слотов и субагентов, нет envelope результатов под каждую модель;
- «дословный replay» подан как универсальное правило, хотя есть обязательные исключения.
Абстракция профиля описана одной строкой. Нужны:
- TokenEngine с моделью возможностей (caps);
- кодек, собранный из «китов»;
- ToolProjector с переупаковкой аргументов;
- политики как данные;
- Grammar IR, компилируемый в GBNF, Lark или маски;
- два драйвера (Native и ChatCompletions) за одним швом.
Тогда Qwen/Nemotron-XML и собственный движок становятся сборкой из готовых частей. Решение о транспорте остаётся прежним. Меняется порядок работ: M1 должен включать Native gpt-oss, токен-нативный транскрипт и сборку llama.cpp с патчем стрима.

## Problems
- **[critical] Пункт «контент — токенизация без спец-токенов → нет инъекций» нельзя реализовать токенизатором llama.cpp: ни через /tokenize с parse_special:false, ни строками внутри смешанного prompt-массива /completion. Структурные токены обеих моделей имеют тип USER_DEFINED, а такие токены распознаются всегда.**
  - why: src/llama-vocab.cpp:3406-3411: при parse_special=false пропускаются только CONTROL и UNKNOWN; USER_DEFINED входят в cache_special_tokens (3178-3180).
- gpt-oss: <|channel|>, <|message|>, <|start|>, <|constrain|> принудительно получают USER_DEFINED (3073-3081), <|end|> тоже (3139).
- Gemma 4: конвертер пишет USER_DEFINED для <|channel>, <channel|>, <|tool_call>, <tool_call|>, <tool_response|>, <|"|> (conversion/gemma.py:646-655).
Следствия: файл с текстом '<|end|><|start|>developer<|message|>...' превратится в поддельное developer-сообщение; литерал <|"|> в коде закроет строку Gemma. Строковые части смешанного массива токенизируются с parse_special=true (server-context.cpp:4926, server-common.cpp:913-945).
Для сравнения: в HF tokenizer.json у обеих моделей все эти токены помечены special=true. Но у локальной nemotron-3.5-lightning токены <think>, <tool_call>, <tool_response> — special=false. Значит, у XML-семейств не поможет даже encode_special_tokens.
  - fix: Токенизировать контент в процессе агента:
- gpt-oss — o200k_harmony через encode_ordinary (вендоренный oss-harmony);
- Gemma — HF tokenizers с set_encode_special_tokens(true);
- семейства с не-special added tokens — базовая BPE/SP-модель вообще без added vocabulary.
В /completion отправлять только массивы ID, без строк.
Жёсткий assert на профиль: ни один content-спан не содержит ID из таблицы added/special токенов. Это касается и MCP-описаний, enum, имён свойств, AGENTS.md, вывода инструментов.
/tokenize оставить только оракулом паритета, с allowlist известных расхождений (напр. #30787, combining marks в o200k на пине).
Generic-путь: санитайзер спец-строк в выводе инструментов и описаниях (word joiner внутри '<|' с обратным маппингом для find/replace) либо запрет такого контента для моделей без Native.
- **[critical] Потоковый /completion на пине теряет ID токенов, после которых UTF-8 неполон, а финальный чанк в stream-режиме токенов не содержит. Инвариант «сгенерированные токены хранятся дословно → нулевое расхождение KV» ломается молча.**
  - why: server-context.cpp:1988-2019: partial отправляется только при полном UTF-8 и несёт res->tokens.assign(1, tkn.tok) (2204), то есть только последний токен. Ранее буферизованные ID теряются. Строки 2243-2246: в режиме stream final отдаёт tokens пустым.
Замер на токенизаторе gpt-oss (scratchpad/review-model/utf8chars.py):
- U+1F680 → [112927, 222], оба токена «неполные»;
- '└──' → [10862, 242, 23386];
- U+26A0 U+FE0F → 3 токена, 2 неполных;
- в строке с эмодзи «неполных» 13 из 24 токенов.
У Gemma (словарь 262K) на тех же образцах — 0. gpt-oss часто выводит дерево файлов и эмодзи, поэтому расхождение префикса KV (на SWA — откат или полный пересчёт) и порча байтов аргументов будут регулярными.
Побочный вывод: EOG-токен в стрим попадает (partial уходит до проверки EOG). Это закрывает «unknown» из обоих отчётов.
Upstream PR #31244 (открыт 27.10.2026) чинит ровно это: на baseline падают 10 из 11 регрессионных тестов.
  - fix: Собирать закреплённую сборку с патчем #31244 или эквивалентом: копить pending-ID и сливать их в следующий partial и в final.
В T0/T2 добавить инварианты: detokenize(stream_ids) == content и число ID == n_decoded.
Фолбэк без патча: сверять n_decoded и восстанавливать пропуск по байтам (однозначно, если потерян один токен), иначе делать запрос без стрима с return_tokens.
Аргументы и тексты собирать из байтов токенов, а не из content (если влить #28724, content может содержать U+FFFD).
- **[critical] Компакция «на границах ходов» не покрывает главный сценарий — длинную агентную задачу внутри одного user-сообщения.**
  - why: - gpt-oss на high переполняет 128K внутри одной задачи (это видно в воспроизведении SWE-bench).
- У Gemma весь tool-цикл живёт внутри одного model turn: ответы инструментов вставляются в тот же turn, граница хода может не наступить вовсе.
- Выбросить CoT внутри незавершённого хода у gpt-oss нельзя: #27720 — 7 битых заголовков из 120 против 0 из 120.
- Gemma слабеет на длинном контексте (MRCR-128K = 44; повторы на большом контексте, #21799).
  - fix: Ввести компакцию посреди хода как новую «эпоху» кеша. Состав: статический префикс → [user: исходная задача + структурное саммари + план + список изменённых файлов и проверок] → последние N шагов дословно, вместе с их CoT или мыслями (пары call/result атомарны) → продолжение генерации.
Порядок мер, всё одним пакетом, а не инкрементально (иначе каждое усечение — отдельный разрыв префикса):
1. усечь старые выводы инструментов;
2. заменить старые шаги саммари;
3. выбросить CoT старше N шагов.
Триггер для gpt-oss — по остатку контекста: n_ctx − prompt < n_predict_cap (≈16K на high) + result_cap + запас. Для Gemma — по эффективному окну, измеренному в T2 (16/48/96K).
Саммари генерировать форком основного слота: префикс там уже закеширован.
- **[major] Абстракция «ModelProfile = TOML + кодек на семейство» слишком тонкая. Не разделены движок, формат, проекция инструментов и политики. У Generic и Native нет общего шва, у бэкенда нет модели возможностей. Третье семейство и собственный движок превратятся в копипасту.**
  - why: Три целевых формата требуют разных парсеров и политик:
- Harmony: recipient и channel в заголовке текстом, вперемешку со спец-токенами; CoT выбрасывается после final.
- Gemma: DSL целиком размечен токенами, tool-цикл внутри одного turn, опция preserve_thinking.
- Qwen3.5/3.6/Nemotron: XML-вызовы <tool_call><function=..><parameter=..> обычным текстом; значения raw до '</parameter>'; <think> — не-special added token (у локального Nemotron); есть политика truncate_history_thinking.
Первым двум нужен ID-автомат, третьему — текстовые разделители с маппингом байт↔токен.
  - fix: Пять слоёв.

- **[major] «Сгенерированные токены вставляются в следующий промпт дословно» как универсальное правило неверно, а местами вредно. Не определено и поведение после ремонтов.**
