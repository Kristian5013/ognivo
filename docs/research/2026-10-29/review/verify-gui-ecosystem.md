# verify: gui-ecosystem

## [PARTIALLY] OpenCode's desktop app moved from Tauri to Electron in April-May 2026, citing WebKitGTK/Linux problems.
**Corrected:** The timing is right. Brendonovich announced the Electron rebuild around 2026-04-18/19 (dev.to post dated 2026-04-19); Tauri and Electron builds shipped side by side for a while. PR #25822 then deleted src-tauri and "replac[ed] the Tauri-based implementation" (merged 2026-05-05), and the README changed to "built with Electron" on 2026-05-06/07. nixpkgs repackaged it on electron_41 (2026-05-11). The reason is wrong: they did not cite WebKitGTK or Linux in particular. Their reasons were: (1) "Tauri uses WebKit on macOS and Linux", which renders their app slower than Chromium and has style inconsistencies, so WKWebView on macOS counts as much as WebKitGTK; (2) the bundled CLI sidecar ('opencode serve') slowed startup and sometimes failed, especially on Windows; (3) they wanted to move the server from Bun to Node and run it inside Electron's own Node process. The post also says Tauri's CEF effort had no clear stable date, and that Tauri is still a good fit when app logic is in Rust.
**Evidence:** https://dev.to/brendonovich/moving-opencode-desktop-to-electron-4hip ; https://github.com/anomalyco/opencode/pull/25822 ; https://github.com/anomalyco/opencode/commit/1219691c114c9aec251bc855b3a4b53f7d12ff14 ; https://github.com/NixOS/nixpkgs/commit/50b75f108d1d0e60dccc694ed98cddedbbe237d7

## [CONFIRMED] WebKitGTK still has documented 2026 issues relevant to an IDE app: NVIDIA DMABUF crashes/workarounds, slow or software WebGL, IME candidate-window mispositioning on Wayland.
**Corrected:** All three are documented in 2026.
(a) NVIDIA/DMABUF. Tauri's official 'Linux Graphics Issues' page (last updated 2026-06-15) lists blank windows, crashes on resize, 'AcceleratedSurfaceDMABuf was unable to construct a complete framebuffer' and Wayland 'Error 71'. Its workarounds are __NV_DISABLE_EXPLICIT_SYNC=1, WEBKIT_DISABLE_DMABUF_RENDERER=1 and WEBKIT_DISABLE_COMPOSITING_MODE=1. tauri#14924 (opened 2026-02-10, still open) covers crashes on NVIDIA 590+ with transparent windows, and tauri PR #16226 (2026-10-07) adds a startup warning for the webkit2gtk 2.44 Wayland DMA-BUF abort. The workaround itself now causes trouble: on WebKitGTK 2.52.x, WEBKIT_DISABLE_DMABUF_RENDERER=1 can SIGSEGV through a null AcceleratedBackingStore (WebKit bug 324730, filed 2026-09-21, status NEW). WEBKIT_DMABUF_RENDERER_FORCE_SHM=1 is the safer option, and Debian/Ubuntu ship disable-nvidia-dmabuf.patch. Disabling DMABUF or compositing falls back to full-window CPU repaints, measured at 40-90 ms per frame on WebKitGTK 2.54.1.
(b) WebGL. The same Tauri page says "WebGL2 context creation succeeds even when the result is backed by a software rasterizer or a slow presentation path". The renderer string is masked as 'Apple GPU', so apps cannot detect this. The page reports high input latency in terminal emulators and editors and recommends a non-WebGL fallback on Linux.
(c) IME. tauri#11412 is still open. A 2026-08-26 reproduction on Ubuntu 26.04 / GNOME 50.1 native Wayland, fcitx5 5.1.19, WebKitGTK 2.52.3 and Tauri 2.11.5 shows the candidate popup landing off-screen after the page scrolls (document vs viewport coordinates). The fix is app-side, calling notify_cursor_area. Separately, wry turns off IME preedit unconditionally with set_enable_preedit(false), and wry PR #1724 to make this configurable is still open. With preedit re-enabled on GNOME Wayland + fcitx5/Mozc + WebKitGTK 2.52.6, the candidate window was placed correctly. So the IME breakage depends on the setup, and it also affects X11.
**Evidence:** https://v2.tauri.app/develop/debug/linux-graphics/ ; https://github.com/tauri-apps/tauri/issues/14924 ; https://github.com/tauri-apps/tauri/pull/16226 ; https://github.com/block/buzz/issues/3654 ; https://bugs.webkit.org/show_bug.cgi?id=324730 ; https://github.com/tauri-apps/tauri/issues/11412#issuecomment-5420366006 ; https://github.com/tauri-apps/wry/pull/1724

## Other corrections
- The draft's 'OpenCode left Tauri' argument carries over to cforge only in part. OpenCode left mainly because its whole server is TypeScript (CLI sidecar, Bun to Node), and its post says Tauri is still a good fit when app logic is in Rust. cforge's agentd is Rust. The WebKit-performance part of their argument applies to both macOS and Linux.
- If the draft keeps 'later switch the shell to Tauri 3 + CEF' as an option: tauri-runtime-cef 3.0.0-alpha.6 pins cef =154.5.0 (Chromium 154) and needs GTK4 on Linux, while the wry runtime uses GTK3. A third-party PR (y4my4my4m/harmony#95) reports the two cannot be loaded in the same Linux process. Tauri 3 is still alpha.5, and stable Tauri is 2.12.5.
- If WebKitGTK is ever used: WEBKIT_DISABLE_DMABUF_RENDERER=1 is no longer a safe blanket workaround on WebKitGTK 2.52+, because it can SIGSEGV (WebKit bug 324730). WEBKIT_DMABUF_RENDERER_FORCE_SHM=1 is the safer choice, and Debian/Ubuntu already disable NVIDIA dmabuf through a distro patch. Tauri's own docs say to give WebGL views (xterm.js, editors) a non-WebGL fallback on Linux. This concern does not apply to the draft's Electron/Chromium choice.
- Draft line 18, 'the best Zed crates are GPL-3.0', is accurate. editor, ui, terminal, terminal_view, markdown, project, language, multi_buffer, lsp, theme and settings are all GPL-3.0-or-later. Only gpui, gpui_macros, gpui_platform, sum_tree, collections, refineable and util are Apache-2.0. Also, gpui on crates.io (0.2.2) is stale compared with main, where gpui_platform is unpublished, so using GPUI means a git dependency.
- Cursor still ships Electron 42.10.0 (Chromium 148) with a VS Code 1.128.0 base as of Sep-Oct 2026. It is not on current Electron 45, which supports the draft's point that VS Code forks lag behind their upstream.
- VS Code's weekly cadence is real and fast: 1.111 in March 2026 to 1.144.0 on 2026-10-28. This supports the draft's 'weekly upstream' argument against forking VS Code.
- Continue is not formally archived on GitHub. Its README marks it read-only and unmaintained, and the last commits to main are from 2026-07-21.
- Electron 45 ships Node 24.22.x, which matches the owner's Node 24 toolchain. xterm.js 6.0.0 (@xterm/xterm) exists, published 2025-12-22, along with @xterm/addon-webgl 0.19.0.
