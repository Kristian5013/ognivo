## [PARTIALLY] In /v1/chat/completions a custom grammar (or json_schema/response_format) cannot be combined with tools - the request is rejected or tools are ignored.
**Corrected:** These two cases behave differently. (a) A custom `grammar` plus non-empty `tools` is rejected with HTTP 400 "Cannot use custom grammar constraints with tools.", but only when tool_choice != "none". The check is `body.contains("grammar")`, so even an empty grammar string trips it. With tool_choice:"none" a grammar is accepted. A second guard in common/chat.cpp throws "Cannot specify grammar with tools". (b) `json_schema` or `response_format` plus tools is never rejected. The gpt-oss handler, the Gemma 4 handler and the generic autoparser all return the response-format parser before the tool-call branch is built. The grammar is then non-lazy, so the model still sees the tools in the rendered prompt but cannot emit a tool call, and none would be parsed. In practice the tools are ignored for these models. This is not universal: the Cohere2MoE handler combines response_format with tool calls. Sending json_schema together with grammar is rejected as "Cannot use both json_schema and grammar", which is a runtime_error and therefore HTTP 500, not 400.

## [PARTIALLY] When the final parse of model output does not match the expected chat format, llama-server returns an error (HTTP 500 or an SSE error event) and the generated text is not returned to the client.
**Corrected:** When the final (non-partial) PEG parse fails, common_chat_peg_parse logs the unparsed tail with LOG_WRN and throws runtime_error "The model produced output that does not match the expected <format> format", where <format> is e.g. peg-native for gpt-oss or peg-gemma4 for Gemma 4. There is no fallback that returns the raw text as content. The throw happens inside server_response_reader::next() during result->update() on the final result. Non-stream: the exception leaves the handler without being caught and ex_wrapper turns it into HTTP 500 server_error, so no text reaches the client. Stream: the exception is caught inside the SSE generator and sent as `data: {"error":{code:500,...}}` (an `event: error` for the Anthropic format), the stream ends and no [DONE] is sent. Any deltas already parsed from earlier partial parses (content, reasoning, tool-call fragments) were already delivered, so in streaming mode only the unparsed remainder is lost. If the first streamed result is already final, the client gets plain HTTP 500. A partial parse that fails at position 0 also throws mid-stream. Upstream master (b11982, 2026-10-29) behaves the same.

## [CONFIRMED] On the chat-completions path the rendered prompt is tokenized with special-token parsing enabled, so literal control-token text inside user/tool message content becomes real control tokens (issue #28249 open).
**Corrected:** Correct. The session prompt is flattened to a single string (`llama_params["prompt"] = out_session.prompt().str()`). It is then tokenized with add_special=true and parse_special=true, both in the text path (tokenize_input_prompts) and in the multimodal path (mtmd_input_text parse_special=true). Any special-token text in user or tool content therefore becomes control tokens. The groundwork for a fix already exists but is not used by the server: the Jinja engine marks user-input parts, and common_chat_prompt carries parts with `is_input` ("special tokens inside must not be parsed"). Issue #28249 "wiring up jinja input marking" is OPEN (created 2026-09-02, no linked PR). Its tasks "Refactor chat.cpp to output parts" and "Wire it up to server" are unchecked; only mtmd_tokenize_from_parts is checked. Upstream master still uses `.str()`.

## [CONFIRMED] tool_choice is parsed only as a string (auto|none|required); the OpenAI object form {type:function,function:{name}} silently becomes auto.
**Corrected:** Correct. The server reads `json_value(body, "tool_choice", std::string("auto"))`. For an object, get<std::string>() throws common_json_error. json_value catches it, logs only a server-side LOG_WRN ("Wrong type supplied for parameter 'tool_choice', using default value") and returns "auto", so the client gets no error. common_chat_tool_choice_parse_oaicompat accepts only "auto", "none" and "required". Any other string gives HTTP 400 "Invalid tool_choice". Without --jinja, any value other than auto is rejected. Related: the Anthropic /v1/messages adapter maps {type:"tool",name} and {type:"any"} to "required", which forces some tool call rather than the named one. Upstream master is unchanged.

## [CONFIRMED] The gpt-oss (Harmony) handler allows only one tool call per generation and constrains arguments with a lazy grammar from the JSON schema; the Gemma 4 handler (common/parsers/gemma4.cpp) constrains only call syntax, not argument schemas (TODO), and allows parallel calls by default.
**Corrected:** Correct, with two nuances. gpt-oss: the parser is zero_or_more(start + analysis|preamble) followed by exactly one (tool_call | final). parallel_tool_calls is never read, so at most one call per generation. Arguments go through p.tool_args(p.schema(json, "tool-N-schema", params)), and the schema becomes GBNF via builder.add_schema. The grammar is lazy, triggered by " to" / "<|channel|>commentary to=functions" patterns, only for tool_choice=auto; with tool_choice=required or a response_format it is non-lazy. Gemma 4: arguments are matched by the generic `gemma4-dict` rule, with a TODO on extending json-schema-to-grammar. Tool names are still restricted to the declared names. Calls repeat with min 1 if required (else 0) and max -1 if parallel_tool_calls (else 1). The default for parallel_tool_calls is the template capability supports_parallel_tool_calls. That capability defaults to true and is true for the official Gemma 4 template, which loops over message['tool_calls'], so parallel calls are allowed unless the request sends parallel_tool_calls:false.

## [CONFIRMED] SWA context checkpoints default to at most 32 per slot with >=8192-token spacing, created at user-message boundaries and near the prompt end; --cache-reuse does not work for iSWA models without --swa-full; --swa-full keeps the full KV for SWA layers.
**Corrected:** Correct, with nuances. n_ctx_checkpoints=32 (-ctxcp/--ctx-checkpoints, alias --swa-checkpoints). checkpoint_min_step=8192 (-cms/--checkpoint-min-step, 0 = no minimum). Checkpoints are made only for completion tasks, and only when the model uses SWA with n_swa>0 (not swa_full) or is a recurrent/hybrid model (seq_rm FULL/RS). They are taken: (1) at batches starting a user message, only if more than 8192 tokens past the previous checkpoint; (2) always at the last user message; (3) near the prompt end, 4+n_ubatch and 4 tokens before it. The oldest are evicted beyond 32, and ones too close together are dropped only when the list is full. User boundaries come from chat-template message spans, which only chat-template endpoints produce. Raw /completion gets only near-end checkpoints. Only the USER role counts, so tool-result turns are not boundaries. cache-reuse requires llama_memory_can_shift. For iSWA that is true only when the base and SWA cache sizes match, which in practice means --swa-full. Otherwise the server disables it at startup with a warning. It is also always disabled when an mmproj is loaded. --swa-full sets the SWA cache size equal to the full context and sets the server's n_swa to 0, so no SWA checkpoints are made. Both reference models are iSWA: gpt-oss sliding_window=128, Gemma 4 sliding_window=1024.

## Other corrections

The control endpoint finds the slot by oaicompat_cmpl_id (server-context.cpp:1682-1694), so reasoning_end control is in practice usable only with OAI-format endpoints that return an `id` (chatcmpl-...).

- With json_schema/response_format plus tools on gpt-oss or Gemma 4, the tools are still rendered into the prompt, but a non-lazy grammar forces the final JSON. The model sees tools it cannot call.

- The Anthropic /v1/messages adapter maps tool_choice {type:'tool',name:X} to 'required'. That forces some tool call, not tool X (tools/server/server-chat.cpp:567-578).
- Error message names on parse failure are 'peg-native' for gpt-oss (COMMON_CHAT_FORMAT_PEG_NATIVE) and 'peg-gemma4' for Gemma 4 (common/chat.cpp:838). Handler dispatch depends on the template source: '<|channel|>' selects gpt-oss, "'<|tool_call>call:'" selects Gemma 4. A Gemma 4 template missing '{#- OpenAI Chat Completions:' gets the legacy workaround (common/chat.cpp:1107-1110, 1214-1220). The local HF Gemma 4 template is the new one (chat_template.jinja:271).
- Upstream master as of 2026-10-29 (latest build b11982) is unchanged on these points: tool_choice parsing, the grammar+tools rejection, the flattened prompt().str(), the throw on parse failure, port 9931, the sampler defaults and the checkpoint defaults.
