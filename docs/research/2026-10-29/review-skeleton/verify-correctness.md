# Verification: correctness

## [REAL · major] A failed /props is reported as 'ik_llama.cpp, class C'; auth and URL mistakes end with exit 0

**Reason.** Checked against the snapshot the findings cite. All line numbers match it; another agent is rewriting the working tree at the same time, so current line numbers differ. diagnose() replaces a failed /props with Props::default() (doctor.rs:130-139), and ServerKind::from_build_info(None) returns IkLlama (caps.rs:18-20), which classify() turns into class C. detect_profile drops every /tokenize error through `if let Ok` (doctor.rs:198), so the report says 'model family not recognised'. Every note is Warn, so has_errors() is false and main.rs:66 exits 0. Upstream 12cc59ba4 skips the API-key check only for /health, /v1/health and UI assets (tools/server/server-http.cpp:252-259); ik skips it for /health, /v1/health, /models, /v1/models and /api/tags (examples/server/server.cpp:667-673). So /props and /tokenize return 401. Upstream registers /v1/health but has no /v1/props or /v1/tokenize (tools/server/server.cpp:171-201), so `--url …/v1` produces the same wrong verdict. The 401 or 404 text does show up in the first Warn, but the server line ('ik_llama.cpp · class C'), the family verdict and the exit code are all wrong.

**Refined fix.** In diagnose(): if /props (or any /tokenize) returns 401 or 403, add Level::Error 'authentication failed: pass --api-key or set OGNIVO_API_KEY' and return. If /props fails any other way (non-200, a body that is not JSON, or JSON that is not an object), add Level::Error with the status and the hint 'use the server root URL, without /v1', leave report.kind and report.class as None (do not map it to class C), and return. Infer IkLlama only from a 200 /props whose body is a JSON object without build_info; never call from_build_info on Props::default(). Make detect_profile return Result and report a non-200 /tokenize as Error instead of 'not recognised'. Optionally strip a trailing '/v1' from --url and print a note.

## [REAL · major] Server errors in the middle of a stream, and streams that end without a final payload, pass as normal

**Reason.** Upstream /completion (TASK_RESPONSE_TYPE_NONE) ends its stream with an empty output and no [DONE] (tools/server/server-context.cpp:5394-5402). A mid-stream error is sent as format_oai_sse({"error":…}) and the stream then ends (:5361-5369, :5435-5439). The begin marker sends a 200 with no body before prefill (:4221-4229; server-task.cpp:1031-1033), so a decode failure such as 'Compute error.' (:4608, :4618) also arrives as an SSE error payload. ik behaves the same way (examples/server/server.cpp:1264-1268, and no [DONE] for OAICOMPAT_TYPE_NONE). token_events (engine.rs:194-222) ignores `error`, and completion_stream treats EOF as a normal end and throws away buf (llama.rs:196). So RawEngine::complete yields neither an Err nor a Done. probe_stream_ids then returns Missing (doctor.rs:305), which leads to class C with the hard-coded '(ik_llama.cpp)' text, or silently returns NotProbed (:306). In the NotProbed case probed=false, so a pinned build prints 'run with --probe to verify' (doctor.rs:169-172) even though --probe was given.

**Refined fix.** Make token_events return Result. If v["error"] is an object, return Err(EngineError::Status { status: error.code as u16 (default 500), body: error.message }); the existing variant has the fields status and body, not code and message. In RawEngine::complete, carry a saw_stop flag through the stream (use scan or unfold instead of the stateless flat_map). At EOF without a stop:true payload, yield Err(Protocol("stream ended without a final payload")). In completion_stream, treat bytes other than whitespace left in buf at EOF as a Protocol error. In probe_stream_ids, treat predicted == None as Err, never as Missing or NotProbed. In diagnose, track whether a probe was requested so a failed probe never prints '(run with --probe to verify)' and always adds a finding. Build the class C message from report.kind instead of hard-coding ik_llama.cpp.

## [REAL · minor] On ik_llama.cpp every stop reason becomes Stop::Other("unknown")

**Reason.** token_events reads only stop_type (engine.rs:209-214). Upstream sends stop_type 'eos', 'word', 'limit' or 'none' (tools/server/server-task.cpp:243-250, 346). ik's final /completion payload is the `data` object built in send_final_response, which carries stopped_eos, stopped_word and stopped_limit but no stop_type (examples/server/server-context.cpp:2608-2626; to_json_non_oaicompat_final returns data; stop_type is commented out at server-task.cpp:82). bench/m0/probes/ik-gpt-oss.json and ik-gemma4.json record stop_type null, while the upstream probes record 'eos'. Rated minor because nothing in M0 reads Done.stop (the doctor ignores it) and Other is a fail-safe default; the Native degraded mode on ik would still never see Eog or Limit. One part of the proposed fix is wrong: 'truncated: true' is not a generation limit on ik. ik sets it on context shift and on prompt truncation (server-context.cpp:3655, 4171), and the n_ctx_train cut already sets stopped_limit (:2336-2337).

**Refined fix.** When stop_type is missing, use ik's booleans in ik's own priority order (send_final_response:2586-2589): stopped_word gives Word, otherwise stopped_eos gives Eog, otherwise stopped_limit gives Limit, otherwise Other("none"). Do not read `truncated`. Add a unit test with ik's final payload: {"content":"","generated_text":"…","stop":true,"stopped_eos":true,"stopped_word":false,"stopped_limit":false,"timings":{"predicted_n":72}} should give Done{Eog, Some(72)}.

## [REAL · minor] No timeout on the /completion stream and 600 s per /tokenize: `doctor --probe` can hang forever

**Reason.** completion_stream sets no timeout, the client has only connect_timeout(5s) (llama.rs:66-70, 166-171), and bytes.next() has no idle limit. Upstream sends the response only when a slot starts the task: the first rd.next waits for the begin marker (tools/server/server-context.cpp:5327-5333, 4221-4229). So with -np 1, which the Gemma and Qwen profiles recommend, and another client generating, `doctor --probe` waits silently until that generation ends. If the decode loop is wedged, the HTTP thread still answers /health, /props and /tokenize, and the probe then never returns. The /tokenize part is overstated: both servers answer it straight from the HTTP handler (upstream server-context.cpp:6252-6290; ik server.cpp:1486-1495), and upstream only waits there to wake from sleep (:5163-5172). The 600 s × 28 'hours' case therefore needs a server that answers /health and /props but stalls on /tokenize. Rated minor because the probe is opt-in and Ctrl-C works.

**Refined fix.** In the doctor, wrap probe_stream_ids in tokio::time::timeout of about 120 s and report a Warn 'stream probe timed out: server busy or not generating'. Optionally check /slots (on ik, /health slots_processing) first and report 'busy' instead of queueing. Lower post()'s timeout for /tokenize and /detokenize to about 30 s. For agent streams, take an idle timeout from the caller instead of a fixed read_timeout of about 90 s: ik sends no SSE pings and no headers until the first token (it has no begin marker), so a long prefill on the CPU-only ik build would trip a 90 s limit. Cancellation should stay the main mechanism there.

## [REAL · major] The template check compares raw file hashes, but llama-server reports a normalised template, so canonical templates are never recognised

**Reason.** /props.chat_template comes from common_chat_templates_source(), which returns template_default->source() (upstream tools/server/server-context.cpp:5560, 5580; common/chat.cpp:795-806). source() is the lexer's output (common/chat.cpp:1339-1344): CR and CRLF become LF, and one trailing '\n' is dropped (common/jinja/lexer.cpp:44-58). Before that, common_chat_templates_init replaces the gpt-oss raise-check line with {%- if false %} (common/chat.cpp:838-846). ik has the same code (common/chat.cpp:624-632, common/chat.h:60-64, common/jinja/lexer.cpp:43-57). Recomputed hashes: gpt-oss canonical a4c9919c… becomes b2215de6da8ba369957eece8c5aa18f4af94f6c4d311d85e691373a421d80e89; Gemma canonical ae53464b… becomes 6a1015c47ccfcfa67c3b772385bccee357a4d37c3cda37bd202e9047f391ab82; the Gemma GGUF template 845f1ee4… becomes aa3185dfc650…, exactly the hash measured in M0; Qwen is unchanged. check_template looks the served hash up in `known` (doctor.rs:374), whose canonical entries are raw file hashes. So after following the doctor's own --chat-template-file advice, gpt-oss and Gemma get 'not in the vetted list'. The M0 note that the server uses its own Gemma 4 template (docs/m0/measurements.md:75) is wrong. Secondary point, also confirmed: read_file opens the path relative to llama-server's working directory (common/arg.cpp:67-75, 3818-3819) and the templates are not embedded, so the copied flags work only from the repo root; the server then fails loudly at startup, not silently.

**Refined fix.** Add a served_form(template) helper: apply the two common_chat_templates_init patches (the gpt-oss raise-check and the Mistral [TOOL_CALLS] check), then the lexer normalisation. Decide whether to strip the trailing newline from the last byte before CR normalisation, convert CRLF and CR to LF, then drop one '\n'. Key every `known` entry by the served hash: replace the canonical entries with b2215de6… (gpt-oss) and 6a1015c4… (Gemma); Qwen stays c3cf9e34…. Keep canonical_sha256 as the pin for the file itself. Extend canonical_templates_match_their_pins to assert that lookup(sha256(served_form(canonical.jinja))) has verdict Canonical. Correct the Gemma note in docs/m0/measurements.md. In the advice and recommended_flags, print the template path as an absolute path, or state that it is relative to the ognivo checkout.

## [REAL · minor] Within a family, the first profile in file order wins on a match anywhere in the full path, and the fallback is silent

**Reason.** detect_profile (doctor.rs:196-218) checks hints with contains() over the whole lowercased model_path and falls back to matches.first() without any note. Each family has exactly one built-in profile today, so the file-order tie-break has no effect yet. The real problem is that the hints cover whole families ('gpt-oss', 'gemma-4', 'qwen3.5', 'qwen35') and the fallback is silent. Any same-family model (gpt-oss-120b, other Gemma 4 sizes, Qwen3.5 models with the 248058 vocabulary) silently gets the reference model's working_max check, recommended_flags (-c, -np, --swa-full) and --chat-template-file advice. Architecture §4 calls for degraded mode with warnings in that case ('остальное работает в деградированном режиме с предупреждениями'). The harm is limited because the output names the profile ('recommended llama-server flags for gpt-oss-20b').

**Refined fix.** Match hints against the GGUF file name (basename of model_path) and /props model_alias (ik: model_name), not against directories. Separate model-specific hints (for example 'gpt-oss-20b', 'gemma-4-26b', 'qwen3.8-27b') from family membership. When only the tokenizer probe or a family hint matched, keep the profile for its codec, add Level::Warn 'family recognised by tokenizer only: <display_name> values (context budget, server flags, template) are not verified for this model', and omit recommended_flags and the template advice. When several profiles match, pick the longest matching hint across all candidates. Add a test with two profiles of the same family.

## [REAL · minor] A stream probe that never hits a split UTF-8 character still counts as 'Complete' and overrides the class from the build

**Reason.** probe_stream_ids reports Complete whenever received == predicted (doctor.rs:298-299). It never checks that the output contained a character split across tokens, the only case where an unfixed build drops ids, and classify gives the probe priority over the build (caps.rs:59-62). With the reference models at greedy decoding the output does contain the emoji line, so a false class A needs an unusual server or model. The cited triggers are confirmed in upstream: requests inherit params_base.sampling (server-schema.cpp:494), an empty request grammar cannot clear a server-wide grammar (:292), and CLI antiprompts apply when the request sends no stop (:500, :466-469). Other triggers: a same-family model that paraphrases, or one that spends the 160-token budget in its analysis channel. received > predicted is also labelled Lossy. The impact is diagnostic only, since §5.4 compares the id count with predicted_n on every generation anyway.

**Refined fix.** Collect the streamed content and accept Complete only if it contains at least one 4-byte probe character (for example '🚀', or any char ≥ U+10000). Otherwise return a new StreamIds::Inconclusive, which classify() treats like NotProbed and the doctor reports as 'probe inconclusive'. Treat received > predicted as Inconclusive (a protocol anomaly), not as Lossy.

## [REAL · minor] 'Neutralise every other sampler' misses server defaults that change or break generation

**Reason.** Upstream starts every request from params_base.sampling (tools/server/server-schema.cpp:494), and a field's handler runs only when its key is in the request (:598-600, :651-660). completion_body (engine.rs:151-190) sends no mirostat, top_n_sigma, dynatemp_range, adaptive_target or samplers, and sends logit_bias only when something is banned. With --ignore-eos the server's default logit_bias already holds the EOG −inf biases (common/common.cpp:1366-1370). A request's ignore_eos:false would not remove them; only a logit_bias key in the request does, because its handler calls clear() (server-schema.cpp:405). ik works the same way: logit_bias is cleared only when present (examples/server/server-context.cpp:1609-1611), and mirostat, top_n_sigma and the rest default to the server's values (:1220-1236). The doctor compares only four values (doctor.rs:341-348), and the comment at engine.rs:163 overstates what the code does. Rated minor because it needs non-default server flags.

**Refined fix.** In completion_body, always send "logit_bias" (an empty array when nothing is banned), plus "ignore_eos": false, "mirostat": 0, "top_n_sigma": -1.0, "dynatemp_range": 0.0 and "adaptive_target": -1.0. Both servers accept these names and ignore keys they do not know. Postpone an explicit "samplers" list until the names are checked for each server kind. In the doctor, add a Warn when /props shows ignore_eos true, mirostat other than 0, top_n_sigma > 0, dynatemp_range > 0, adaptive_target ≥ 0 or a non-default samplers order. Make the comment list what is actually neutralised.

**Refined fix.** In Props::from_json, use `let params = if settings["params"].is_object() { &settings["params"] } else { settings };`. Add a test with ik's flat layout, and apply the same fallback in scripts/probe/server_caps.py.

## [REAL · minor] Class A depends on an exact 9-character commit prefix: short hashes and future upstream builds are missed

**Reason.** COMPLETE_ID_COMMITS is ["12cc59ba4"] and classify uses c.starts_with(k) (caps.rs:55, 67). The commit in build_info comes from `git rev-parse --short HEAD` (cmake/build-info.cmake:21; common/build-info.cpp.in:28), whose automatic length depends on the number of objects in the clone. A shallow clone of the PR head therefore reports 'b1-12cc59b', is classed B, and is told to rebuild with the PR it already contains. scripts/llama/build-pinned.sh does a full clone, so the owner's own build reports 9 characters; this is an edge case. An unprobed class B is also stated as fact ('are lossy', doctor.rs:173-177), which will be wrong for every upstream build after the PR merges until the list is updated.

**Refined fix.** Store the full SHA 12cc59ba491447e9c7e58360e857bff11801f3b5 and count it as a match when commit.len() >= 7 and the full SHA starts with the reported commit. When the server was not probed, word class B as 'expected lossy (build not known to include PR #31244); run with --probe to check'. Add a build-number threshold once the PR is merged upstream.

## [REAL · minor] llama-server router mode is reported as 'model family not recognised' with n_ctx 0

**Reason.** Without ?model=, the router's /props returns role 'router', model_path 'none', default_generation_settings {params:{}, n_ctx:0} and build_info, with no total_slots (tools/server/server-models.cpp:2164-2190). The router routes /tokenize to proxy_post (tools/server/server.cpp:476), which requires "model" in the body and otherwise returns 400 'model name is missing from the request' (server-models.cpp:2092-2096, 2227-2234). detect_profile swallows that error (doctor.rs:198), so the doctor warns 'model family not recognised', prints n_ctx 0 as a real value, and exits 0. Architecture §4 lists llama-router as an endpoint type, so this is in scope, although the doctor cannot select a model yet.

**Refined fix.** Read /props.role. If it is "router", add a finding (Warn or Error) 'llama-server router: per-model checks need a model name; GET /models lists them', skip tokenizer-based detection, and do not report n_ctx 0. Later, add a --model option and send ?model= on GETs and "model" in POST bodies.

## [REAL · minor] Both servers reject a Trigger::Word that is a single token, because preserved_tokens is never sent

**Reason.** completion_body sends {"type":1,"value":w} without preserved_tokens (engine.rs:186). Upstream common_sampling_add_grammar_triggers throws 'Grammar trigger word should be marked as preserved token' for a single-token word that is not in preserved_tokens (common/sampling.cpp:1068-1075), and ik does the same (examples/server/server-context.cpp:1544-1551). For Qwen, <tool_call> is the single token 248058, so a codec following §5.4 with Trigger::Word("<tool_call>") would fail every constrained request. The M0 check used 'ANSWER:', which spans several tokens. Rated minor because no codec uses Word yet and the failure is loud. This matters for the fix: ik rejects client TOKEN-type triggers outright with 'Unknown grammar trigger type' (examples/server/server-context.cpp:1563-1574). So the proposed alternative of resolving single-token words to Trigger::Token would break on ik, and the existing Trigger::Token serialisation (type 0, covered by body_sets_lazy_token_trigger) already fails there.

**Refined fix.** For Trigger::Word, also send "preserved_tokens": [word]. Both servers skip entries that span several tokens, and both read preserved_tokens before grammar_triggers (upstream server-schema.cpp:335-347; ik server-context.cpp:1524-1539). Serialise Trigger::Token the same way, as {"type":1,"value":text} plus "preserved_tokens":[text]. Both servers turn a preserved single-token word into a token trigger internally (upstream sampling.cpp:1071-1080; ik server-context.cpp:1547-1557), so this also works on ik. Note that upstream then includes that token's text in `content` (server-context.cpp:4705-4708); this does no harm because arguments are built from token bytes. Add request-body tests for both trigger variants.
