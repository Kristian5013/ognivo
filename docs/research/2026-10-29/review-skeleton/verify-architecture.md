## [REAL · major] RawEngine stream has no reliable terminal event: mid-stream server errors vanish, ik stop reasons become "unknown"

**Reason.** Confirmed against the reviewed code and the server sources. Pinned upstream sends a mid-stream failure as `data: {"error":{...}}` and closes (tools/server/server-context.cpp:5434-5439); the old b11681 build does the same (:5044, :5112-5114). /completion uses response type NONE and never sends [DONE] (:5392-5402). ik does the same (examples/server/server.cpp:1266-1268). The reviewed `token_events` (engine.rs:194-222) produced no event for an error payload, and `completion_stream` simply returned None at EOF (llama.rs:193-197). The consumer therefore saw a clean end of stream with neither Done nor Err. ik's final payload has only stopped_eos/stopped_word/stopped_limit (ik server-context.cpp:2620-2622), and bench/m0/probes/ik-*.json record stop_type null, so every class-C Done was Other("unknown"). M0 already produced such an error at generation time (old-gpt-oss.server.log:32-33, 'Unexpected empty grammar stack' in slot iterate), and doctor --probe turned it silently into NotProbed. In M2 this would let a truncated call look complete, which §6 forbids. Already fixed in the current tree: error payloads become Err(Status) (engine.rs:288-299), Stop falls back to the stopped_* booleans (:315-325), `terminated()` emits Err(Protocol) when the stream closes without a final payload (:194-230), the contract is documented (:150-151), and there are tests (:374-400).

**Refined fix.** Keep the current `terminated()` and `token_events` changes and their tests; nothing more for M0. When the M2 loop lands it must treat any Err item, or a stream without Done, as 'call not closed', and never seal or execute that call (§6).

## [NOT REAL · minor] The M1 seam (ModelDriver and its history/event types) is missing while the M2 seam exists

**Reason.** The description is accurate, but this is not a defect of the M0 code. The plan deliberately delivers ModelDriver in M1 together with the loop: lib.rs:12-13 says the seam arrives with its first implementation in M1–M3, §13 lists 'Цикл и драйвер' under M1, and M0 is 'Скелет, CI'. There is no loop and no caller that could be written against the wrong types, so nothing is reproducible. TokenEngine is indeed not dyn-compatible: I confirmed E0038 on rustc 1.99.0 from /tmp/claude-1000/-home-kristian--------------cforge/3ff4d0f1-90d6-4891-b9a2-ce2beecbc699/scratchpad/verify-dyn, because `tokenize` and `complete` return `impl Trait`. That matches the documented design `NativeDriver<Codec, TokenEngine>` (§5.1): the engine is a generic parameter, and ModelDriver is the place for dyn dispatch. The SSE reader is tied to /completion, but generalising it is a one-line change when ChatCompletionsDriver needs it. The failure scenario is a process risk, not something the code does.

**Refined fix.** No change in M0. Make it the first M1 task, before the loop is written. Define a dyn-compatible ModelDriver (boxed future and stream) with HistoryItem (reasoning kept verbatim, plus nullable sealed ids and codec version matching ognivo-store Record) and DriverEvent (deltas, tool call, usage, and a finish reason of Eog, Length, ContextFull or Error). Hold it per session as Box<dyn ModelDriver>, keep TokenEngine generic inside NativeDriver, and let `completion_stream` take the path so ChatCompletionsDriver can reuse the SSE reader.

## [REAL · minor] Profile schema: reasoning set twice, no per-phase sampling, provenance only in comments, no min build, no partial overrides

**Reason.** Only the first point was a real defect. The reviewed profiles set effort and thinking twice: as `[reasoning].default`, a free String (profile.rs:125-131), and again in `[template].kwargs` (reasoning_effort for gpt-oss; reasoning_effort, enable_thinking and preserve_thinking for Qwen; enable_thinking and preserve_thinking for Gemma). No test kept the two in sync, and nothing validated the level. A Qwen profile with default 'high' would parse, although its own comment calls that value an error. Nothing consumed either value in M0, so this was latent drift rather than a live bug; it was cheap to fix. The other points are not M0 defects. The presence_penalty scenario misreads the research: 1.5 applies only to non-thinking prose (qwen38.md:279-281). The Qwen profile runs in thinking mode, where the research prescribes presence 0, frequency 0, repeat 1.0, dry 0 and xtc 0, exactly what completion_body sends. Per-phase sampling, subagent effort (M2), structured provenance, min_build and partial user overrides are all additive features for the milestones that consume them. No eval runs exist yet to cite as provenance, there is no 'verified' status for min_build to gate, and there is no override loader yet (M1). The finding itself calls provenance 'purely additive'. Fixed in the current tree: `[reasoning].levels` was added and `default` is checked against it, and reasoning keys are banned from `[template].kwargs`. **Refined fix.** Keep the current single source in `[reasoning]`, the derived kwargs and the consistency tests. Defer the rest to the milestones that need it. One small UX issue is still open: recommended_flags and doctor's `--chat-template-file profiles/templates/...` hint are repo-relative, so they only work if llama-server starts from the repo root. ## [REAL · minor] Constraint seam: one Token/Word trigger, no PATTERN or preserved_tokens, raw GBNF, trigger invariant not enforced

**Reason.** The llama.cpp facts check out in the pinned source. Triggers are a list of WORD, PATTERN, PATTERN_FULL and TOKEN (common/sampling.cpp:225-258). The grammar starts at the first non-empty capture group, or at the match start (src/llama-grammar.cpp:384-398). llama.cpp's own gpt-oss parser uses four PATTERN triggers to cover both header forms (common/parsers/gpt-oss.cpp:144-149). A single-token WORD trigger throws unless it is preserved (common/sampling.cpp:1068-1075). The reviewed `Constraint { gbnf, trigger }`, with Token or Word only (engine.rs:48-60), could not express what the M2 Harmony codec needs, so the seam had the wrong shape. Impact in M0 was nil, hence minor rather than major. Constraint had no caller besides a unit test. The Qwen example fails loudly with an HTTP error on the first request rather than silently, and Trigger::Token already covered single-token triggers. 'Raw GBNF ties the seam to llama.cpp' is not a defect: in §5.1 the codec emits Grammar IR and the engine takes a compiled constraint, and GBNF is llama.cpp's compiled form. Enforcing 'grammar starts at the trigger' belongs in the M2 grammar compiler. Fixed in the current tree: `triggers: Vec<Trigger>` with Pattern and PatternFull, `preserved_tokens`, serialization as types 0-3, and a body test (engine.rs:48-92, 265-282).

**Refined fix.** Keep the current Vec<Trigger> and preserved_tokens. Two small corrections to the new code. (1) The 'harmless otherwise' comment in Constraint::new is not quite right: preserving a single-token word also makes the server print that special token's text into the streamed `content` (pinned server-context.cpp:4706-4709, 4791). Codecs should prefer Trigger::Token for single-token triggers and Pattern for header context. (2) The fields are pub, so a caller can skip the auto-preservation in `new`; make them private or document `new` as the only constructor. Leave Grammar IR lowering and the start-at-trigger invariant to the M2 grammar compiler, for example a compile step that prefixes the root with the trigger alternatives, and add a body test for the Harmony pattern set.

## [REAL · minor] Store persists the client wire type: raw ids travel as unsealed client deltas, and the seq scope contradicts itself

**Reason.** Confirmed in the reviewed code. The protocol documented Seq as 'Position in a thread's append-only event log' (protocol lib.rs:24-25), but MemoryLog numbers events globally. `append` expects last_seq()+1 across all threads (store lib.rs:31, 50), and the replay test interleaves threads a/b/a with seq 1/2/3. A store written to the documented scheme rejects the first event of a second thread as OutOfOrder. Delta::Tokens was documented as 'kept so the next prompt replays them verbatim' (protocol lib.rs:71-74). That contradicts seal() in §5.4: `<|return|>` becomes `<|end|>`, and a segment is re-rendered canonically after an L1 repair. So the streamed ids are not what must be replayed, and the event model had no place for sealed ids or the codec version (§5.1, §11). One sub-claim is overstated: clients do use tokens, in the Inspector (§10). Fixed in the current tree: seq is documented as global and dense (protocol lib.rs:24-26, store lib.rs:37), the store keeps `Record { event, sealed_ids, codec }` (store lib.rs:11-28), and Delta::Tokens is gone, with the Inspector fetching ids on demand (protocol lib.rs:66-73). Tests were updated.

**Refined fix.** Keep the current Record and global seq. In the M1 SQLite store, map Record.sealed_ids and codec to the nullable columns described in §11, written only on ItemCompleted. Add an Inspector RPC that reads them, since the event stream no longer carries ids.
