Ещё три наблюдения:
- **Ленивая грамматика сопоставляется начиная с текста триггера.** Если GBNF начинается не с триггера, сервер отвечает HTTP 500 `Unexpected empty grammar stack`. Значит, грамматики агента должны начинаться с самого триггера: Gemma — `<[48]>`, gpt-oss — заголовок вызова.
- **Хеши шаблонов.** `/props` отдаёт шаблон в «серверной форме», а не байт-в-байт из GGUF. llama.cpp нормализует его: CR/CRLF → LF, срезан один финальный `\n`; у gpt-oss ещё и подменена одна проверка `raise_exception`. Поэтому у Gemma `/props` = `aa3185dfc650…`, а файл в GGUF = `845f1ee48e39…`: это тот же шаблон Unsloth после нормализации, а не «своя» версия сервера (первоначальный вывод M0 был ошибкой, исправлено по ревью). Преобразование повторено в `ognivo_models::template::served_form` и сверено на всех трёх GGUF; профили хранят хеши серверной формы. Доктор сверяет именно их.
- **В GGUF Qwen3.8 есть MTP-тензоры** (`blk.64.nextn.*`), llama.cpp их пропускает с предупреждением.

## Выводы для архитектуры

1. **gpt-oss и Gemma 4 быстрее оценок из ресёрча.** Те оценки получены масштабированием с десктопной 5090.
   - gpt-oss: генерация 169 ток/с, префилл 12,6K ток/с.
   - Gemma 4: генерация 157 ток/с, префилл 7,7K ток/с.
   - Интерактивная работа на 32–64K контекста комфортна. Промах кеша на 64K стоит 10–14 с — заметно, но терпимо.
2. **Qwen3.8-27B медленнее в 3,5–4,5 раза.** Причины: dense 27B на 896 ГБ/с и гибридная архитектура.
   - 46 ток/с генерации: шаг из 2K токенов reasoning — это примерно 45 с.
   - Промах кеша на 64K — около 48 с.
   - Отсюда требования к его профилю (уточнены ресёрчем `docs/research/2026-10-29/qwen38.md`):
     - строгий append-only. У каждой последовательности есть рекуррентное состояние Gated DeltaNet на 150 МиБ, и откатить его нельзя. Сервер переиспользует только точный префикс;
     - рабочий контекст до 96K, компакция около 90K. Дальше 130K модель внезапно выдаёт EOS (#27756), а генерация падает с 46 до 34 ток/с;
     - проверка MTP только через длительный прогон (soak test). В GGUF уже есть `nextn`-тензоры (llama.cpp пока их игнорирует), отдельный MTP-драфт тоже лежит у вас.
   - **По качеству это, вероятно, сильнейшая из трёх моделей:** Terminal-Bench 2.1 у неё 58–73 (вендор и vals.ai) против ≈14 у gpt-oss и 39 у Gemma; SWE-bench Verified 86% (vals.ai). По скорости она уступает двум MoE. Отсюда роль: «тяжёлый» исполнитель там, где качество важнее времени.
3. **Субагенты.**
   - 4 потока дают суммарно ×2,3 (gpt-oss), ×2,5 (Gemma) и ×2,9 (Qwen). Каждый отдельный поток при этом работает на 57–73% от одиночной скорости.
   - Параллельное исследование кода четырьмя субагентами окупается.
   - Пока основной агент ждёт результаты субагентов, его скорость не важна. Но фоновые субагенты замедляют основного агента примерно на треть. Нужен приоритет: основной агент выше фоновых (§4 архитектуры).
4. **Бюджеты компакции по умолчанию** (калибровать по eval):
   - gpt-oss — до 96K;
   - Gemma 4 — до 64K (MRCR-128K 44%);
   - Qwen3.8 — до 96K, компакция около 90K.
5. **Классы серверов для caps** (§4 архитектуры):
   - **A — upstream с PR #31244 или с влитым фиксом.** Native-путь с дословным повтором токенов.
   - **B — upstream без фикса.** Native-путь работает, но потерянные ID восстанавливаются ретокенизацией сгенерированного текста. Где ретокенизация разошлась с тем, что сэмплировала модель, KV расходится; это дешёвый пересчёт от чекпоинта на конце прошлого промпта.
   - **C — ik_llama.cpp.** ID нет совсем, поэтому Native только в урезанном режиме (всегда ретокенизация), полноценный путь — Generic. Признак ik: `build_info == null`.
6. **Защита от подмены служебных токенов подтверждена как обязательная** на всех серверах. На ik даже `parse_special=false` ничего не меняет, поэтому единственная надёжная защита — разрезать служебные строки в содержимом до отправки в `/tokenize`.
7. **EOG-токен приходит в потоке ID.** Кодек решает по нему, как закрыть сообщение (`seal()`): у gpt-oss `<|return|>` заменяется на `<|end|>`, у Gemma токен 50 открывает ответ инструмента.
