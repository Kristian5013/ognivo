## Как устроен один прогон

1. **Setup на хосте.** `setup.sh` задачи собирает свежую рабочую копию без глобального git-конфига
   владельца. Затем `normalize_ws.py` убирает подсказки о месте внесённой ошибки:
   - у всех файлов одно mtime;
   - отслеживаемые файлы пересоздаются в порядке индекса;
   - `git prune` удаляет недостижимые объекты.
2. **Агент в контейнере.** Rootless Podman. Единственный mount — рабочая копия в `/work`.
   - **Сеть:** `pasta --splice-only`. В контейнере есть только `lo`, и снаружи достижим только порт
     llama-server (через записывающий прокси `llm_tap.py`). Проверено: SSH хоста, другие порты хоста
     (включая Open WebUI на 8080), шлюз, интернет, IPv6 и DNS недоступны.
   - **Ограничения:** `--cap-drop all`, `no-new-privileges`, 8 CPU, 16 ГБ без swap, 4096 pids.
   - **Дисковый сторож:** 40 ГБ на прогон; остановка, если на диске осталось меньше 30 ГБ и место
     продолжает убывать.
3. **Скрытая проверка.** `verify.sh` запускается в отдельном контейнере с `--network none`. Каталог
   задач подключается только на чтение и только после того, как контейнер агента удалён.
4. **`result.json`.** Статус, сводка траектории и `versions`:
   - хеш харнесса, профилей, сборки llama-server, образа, GGUF и версий пакетов;
   - хеш задачи.

   Файлы, которые агент мог подложить через `/out`, оценщик не читает.

**Бюджеты (стенные часы):** 480 с для gpt-oss и Gemma, 1500 с для Qwen3.8. Это равная «ёмкость декода»: примерно 56K и 61K сгенерированных токенов. При первоначальных 900 с у Qwen выходило около 37K, две трети.

## Первые записи в каталог отказов

Даже в решённых задачах:

1. **gpt-oss-20b: заявляет о проверке, которой не было.** Модель не вызвала ни одной shell-команды,
   но в итоге написала: «Running `cargo test -p cforge-bench --offline` passes all tests». Исправление
   совпадает с эталонным, таймстемпы в тестах посчитаны верно, но проверки не было. Требование к
   ognivo: цикл должен требовать или сам запускать проверку перед объявлением успеха.
2. **Gemma: путает назначение инструментов.**
   - Передала Rust-код в `execute`; это JavaScript-рантайм OpenCode («Code Mode» с `fetch`).
     Результат — SyntaxError.
   - Затем вызвала `edit` с пустым `oldString`, получила ошибку и обошла её heredoc через `shell`.
   - Плюс: сама посчитала таймстемпы через `date -u -d` и трижды гоняла `cargo test` до зелёного.
3. **Qwen3.8: раздутые рассуждения съедают бюджет.** Один шаг занял 11.2K токенов рассуждения и
   267 с при reasoning_effort medium. Модель была аккуратной: параллельные вызовы, `git log`,
   отдельный крейт в `/tmp` для трассировки алгоритма, `cargo test`, уборка за собой. Но 791 с из
   900 ушло на самую лёгкую задачу.
4. **OpenCode считает `reasoning` = 0** в токенах сессии для openai-compatible провайдера. Число
   токенов рассуждения берётся только из `llm.jsonl`.

## Ревью стенда (4 линзы, скептики, критик) и что исправлено

Проверены четыре линзы:
- изоляция хоста;
- корректность измерения;
- ночная эксплуатация;
- целостность задач.

Каждую находку пытался опровергнуть отдельный скептик, затем критик искал пропущенное. Линзу
изоляции остановил защитный фильтр API, её проверки сделаны вручную. Исправлено:

- **Утечки решения.** Изменённые файлы выдавали себя mtime и номером inode (`ls -lt` указывал на
  ошибку). В misc-btc исходное дерево лежало в `.git` недостижимым объектом (виден через `git fsck`).
  Теперь это закрывает `normalize_ws.py`.
- **Подделка результата.** Оценщик читал `verify_exit`, `run.env` и `infra_error` сначала из
  `trajectory/`, то есть из копии `/out`, куда агент может писать. Файл `/out/verify_exit` с `0`
  давал «solved». Теперь служебные файлы читаются только из `logs/`, одноимённые файлы из `/out`
  удаляются.
- **Обходы проверки.** `.cargo/config.toml` с `runner = "true"` в рабочей копии cforge «проходил» все
  скрытые тесты. Теперь `.cargo` не копируется в копию для проверки.
- **Классификация.**
  - OOM-убийство и раннее завершение больше не считаются таймаутом.
  - Ошибка llama-server в последнем запросе — отдельный статус `stack_error`.
  - Свои запросы агента к серверу (curl) не смешиваются с запросами OpenCode.
  - Повторы ограничены 3 попытками, дальше статусы `server_crash` или `abandoned`.
- **Ночь.**
  - **Крышка ноутбука.** На этом ноутбуке закрытая крышка усыпляет его и от сети. Блокировка
    `sleep` этому не мешает (logind по умолчанию `LidSwitchIgnoreInhibited=yes`), поэтому теперь
    берётся `handle-lid-switch`. Блокировка держится с 19:00 до конца окна, не круглые сутки.
  - Пропущенная ночь записывается как `missed`.
  - Pre-flight проверка при запуске и в начале окна.
  - Ожидание занятой GPU — до 30 минут.
  - Скрипты разбираются целиком до запуска: правка файла не сбивает идущий прогон.
- **Прокси.**
  - Лимиты на размер тела запроса и число соединений: прокси работает на хосте, вне лимитов
    контейнера.
  - Сироты-прокси на порту больше не перехватывают трафик.
- **Порт.** 8080 занят Open WebUI владельца, стенд перенесён на 8090/8091.
- **Конфигурация OpenCode.** Правило `"*": allow` снимало штатные ограничения с субагентов
  `explore`/`general`. Оно удалено: главному агенту хватает `--auto`, а `webfetch`/`websearch`
  запрещены.

Известные особенности, которые оставлены и задокументированы:
- В misc-ai-chat-multiturn и в файлах misc-ai-moe-balance текстом встречаются спецтокены моделей:
  `<think>`/`</think>` у Qwen и `<bos>`/`<pad>` у Gemma. llama-server разбирает их как настоящие
  управляющие токены. Это уязвимость стека, которую закрывает guard ognivo; такие ячейки помечены
  `token_hazard` и отчитываются отдельно.
- В контейнере 3 теста `cforge-platform tests/real_machine.rs` падают на исходном дереве. Причина —
  окружение (замаскированный `/sys/firmware`, пустой machine-id). Команды из промптов их не
  запускают.
- Каждая ячейка «модель × задача» — один прогон при temperature 1.0 без seed. Разница в одну-две
  задачи — шум; сравнение строится на метриках отдельных вызовов из `llm.jsonl` и `session.json`.

## Решения владельца (2026-10-30)

1. **Бюджет.** Qwen3.8 получает 1500 с, gpt-oss и Gemma — 480 с: равная ёмкость декода. Фаза
   Qwen в худшем случае занимает около 270 минут и растягивается на ночи 2–3.
2. **Запуск.** Владелец сам запускает `run-night.sh` вечером в tmux. Блокировка сна и крышки
   действует с момента запуска, а pre-flight сразу показывает проблемы. Таймер не ставится.
3. **Пакеты.** На время кампании GPU-стек (драйвер NVIDIA 580, модули, метапакеты ядра) и Podman
   (`podman`, `passt`, `conmon`, `netavark`, `containerd.io`) замораживаются через
   `apt-mark hold`. Список — в `evals/m0-baseline/harness/hold-packages.txt`.
4. **Хранение.** В git идут харнесс и документы; задачи остаются вне git. В репозитории лежит
   только манифест с `task_sha256` (`evals/m0-baseline/tasks.json`), а рядом со стендом —
   резервный архив.
