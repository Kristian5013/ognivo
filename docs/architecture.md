# ognivo — архитектура v1

Статус: черновик 2026-10-29, после ответов владельца на вопросы 1–22.
Имя проекта — **ognivo** (огниво; выбрано 2026-10-29, рабочее имя было «forge»).
Доказательная база: `docs/research/2026-10-29/`. Там 8 тематических отчётов с источниками (`*.md` — выводы, `*.findings.md` — факты со ссылками), а в `review/` — адверсариальная проверка ключевых фактов и три критики черновика.
Цифры скорости — оценки, пока нет своих замеров (этап M0).

## 1. Что строим

ognivo — агент для программирования уровня Claude Code / Cline, но только для локальных моделей через llama.cpp. v1 — **агентный воркспейс** (класс Cursor 3 Agents Window / Codex app), а не IDE.

Главное требование: агент идеален под каждую архитектуру модели. Формат промпта, tool calling, reasoning, MCP и терминал целиком на стороне агента.

Эталонные модели v1:
- gpt-oss-20b — Harmony;
- Gemma 4 26B A4B — нативный DSL вызовов;
- Qwen3.8-27B — XML-вызовы.

## 2. Языки и стек

- **Rust — всё, что является агентом.** Сюда входят:
  - ядро, агентный цикл, профили и кодеки моделей, роутер серверов;
  - инструменты, терминал, MCP-клиент, чекпоинты, хранилище;
  - CLI и eval-харнесс.

  Почему Rust:
  - официальный MCP SDK `rmcp` (Tier 1, поддерживает обе «эпохи» спецификации);
  - крейты для PTY, VT-эмуляции, tree-sitter, gix;
  - Apache-2.0 код Codex для переиспользования (apply-patch, идеи execpolicy и песочницы);
  - один статический бинарник.
- **TypeScript + React 19 — только клиенты.** Это Electron-GUI и webview расширения VS Code. Типы протокола генерируются из Rust (serde + schemars + ts-rs).
- **Python — только в разработке.** Golden-тесты шаблонов через Jinja2 (эталон семантики HF), Harbor / Terminal-Bench и SWE-подмножества. В продукт не входит.
- **Своего C++ нет.** llama.cpp остаётся внешним сервером.

Почему не pure-Rust GUI и не Tauri.
- У GPUI, egui, iced, Slint и Dioxus нет готовых редактора, ревью диффов, терминала и стримингового markdown production-уровня. Официальный `gpui` на crates.io застрял на 0.2.2 (2025-10-22). Лучшие крейты Zed под GPL-3.0.
- Tauri v2 на Linux рендерит через WebKitGTK. У него лаги, проблемы с NVIDIA DMABUF и медленный WebGL для xterm.js. CEF-рантайм есть только в Tauri 3 alpha.
- Electron 45 (Chromium 156, Node 24) — это стек Cursor, VS Code, ChatGPT/Codex desktop и OpenCode desktop.

## 3. Процессы

```
 Electron GUI (React)      VS Code extension (webview, те же компоненты)      ognivo CLI
        │ MessageChannelMain              │                                    │
   Electron main ── Unix socket (SO_PEERCRED, 0600) ──────────────────────────┤ (in-process
        └──────────────────────────────┐  │                                    │  или attach)
                                ┌──────▼──▼──────────────────────────────────▼─────┐
                                │ ognivo core (Rust, один на пользователя)           │
                                │ сессии · агентный цикл · субагенты · контекст     │
                                │ слой моделей (драйверы, кодеки, профили)          │
                                │ роутер серверов · tool gateway · MCP-клиент       │
                                │ exec (pipes/PTY) · чекпоинты · approvals          │
                                │ SQLite event log · трейсы                         │
                                └──────┬───────────────────────────┬───────────────┘
                     HTTP (TCP / UDS)  │                           │ stdio / HTTP
          llama-server · ik_llama.cpp · llama-server router (LAN)   MCP-серверы, команды
```

- **Ядро одно на пользователя.** Сокет — `$XDG_RUNTIME_DIR/ognivo/core.sock`. Клиент подключается к уже запущенному ядру или запускает его под lock-файлом. Ядро завершается, когда нет клиентов и активных агентов. Так два клиента не делят одни слоты llama-server вслепую.
- **Транспорт клиентов:**
  - renderer ⇄ main через MessageChannelMain;
  - main ⇄ core — JSON-RPC 2.0 по Unix-сокету с проверкой UID;
  - TCP-слушателя нет (локальный доступ, защита от CSWSH и DNS rebinding);
  - `ognivo run` может встраивать ядро в процесс (headless, eval).
- **Протокол** по образцу Codex app-server: Thread → Turn → Item. Жизненный цикл item: `started` → дельты → `completed`.
  - Подтверждения — запросы сервер→клиент.
  - Переподключение — повтор событий из SQLite с `seq`. Без AHP-снапшотов и мультиклиентского reducer.
  - Модель событий замораживается на выходе из M2. До этого существуют только Rust-типы и JSONL-трейсы.
  - M2: заморожена 2026-11-03 как версия 1 (`ognivo-protocol`).
    - **Тред — это сессия**: пользователя или субагента. Тред субагента называет тред и элемент, на которые работает.
    - **События:** `thread_started` (проект, профиль, уровень, сервер, модель за роутером, родитель), `turn_started` (сообщение пользователя или задача субагента), `item_started`, `item_delta` (текст), `item_completed`, `generation` (токены промпта, из кеша и сгенерированные, время, seed, исход, sha256 запроса), `turn_completed` (чем кончился ход, почему, принятый ответ, статус проверки). `seq` растёт по всем тредам.
    - **Элементы:**
      - `agent_message` и `reasoning` идут дельтами текста;
      - `tool_call` несёт вызов, каким его исполняет ognivo: имя по Claude Code (`Read`, `Edit`, `Bash`, `ApplyPatch`, `Task`…) и аргументы по-ognivo, какими бы их ни назвала модель. В нём же результат (ok, error, refused или skipped, код выхода команды, длительность) и диффы изменённых файлов;
      - `notice` — заметки ognivo модели;
      - `void` — генерация, которая ничего не исполнила: malformed, empty, truncated, repeating или restarted, с её вызовами;
      - `compaction`;
      - `approval` — вопрос, затем ответ;
      - `instructions` — файлы инструкций;
      - `subagent` — его тред и чем он кончил.
    - **`started` и `completed` несут элемент целиком**, дельты нужны только живому показу. Клиент, пропустивший дельты, к концу элемента ничего не теряет.
    - **Дальше только добавления:** новые события, виды элементов и поля. Клиент пропускает то, чего не знает. MCP (M3) придёт как `tool_call` с новым вариантом вызова.
    - **Источник.** Ядро делает модель из событий агента (`ognivo_core::protocol::Projector`). `ognivo run --events` пишет её строками JSON.
    - **TS-типы** генерирует ts-rs в `apps/ui/src/protocol.ts`, и тест сверяет их с Rust-типами.
    - **Golden-поток** `apps/ui/fixtures/stream.jsonl` — ход со всеми видами элементов. Его сверяет тест проектора, а тест UI проигрывает: `src/live.ts` сворачивает поток в хранилище треда.
    - **Чего ещё нет** (M4): сокет ядра с JSON-RPC, подтверждения как запросы ядра к клиенту, повтор по `seq` из хранилища. GUI пока показывает компакцию, вопросы, инструкции и субагентов заметками.
  - M4: ядро подключено 2026-11-03 (`ognivo core`, `crates/ognivo-cli/src/serve*`).
    - **Сокет и запуск.**
      - Ядро слушает `$XDG_RUNTIME_DIR/ognivo/core.sock` (или `--socket`). Каталог создаётся с правами 0700, сокет — 0600, а каждого подключившегося ядро проверяет по UID через `SO_PEERCRED`. TCP-слушателя нет.
      - Одно ядро на каталог данных: оно держит lock-файл `core.lock`, потому что нумерует поток клиентов в хранилище. Второе ядро выходит с кодом 1. Файл сокета, на котором никто не отвечает, считается оставшимся от упавшего ядра и удаляется.
      - Ядро завершается, когда `--idle` секунд (по умолчанию 60) нет ни клиентов, ни идущих ходов, или по SIGTERM. Открытые треды при этом закрываются, как `/exit` закрывает chat, и остаются в хранилище.
    - **Протокол** — JSON-RPC 2.0, одно сообщение на строку (`ognivo_protocol::rpc`, только добавления к версии 1). TS-типы, карта методов `Methods` и вопросов ядра `Asks` генерируются в тот же `protocol.ts`.
      - Методы: `initialize`, `thread/list`, `thread/start`, `thread/resume`, `thread/read`, `thread/trajectory`, `thread/clear`, `thread/close`, `turn/start`, `turn/interrupt`, `turn/answer_now`, `changes/list`, `changes/accept`, `changes/revert`.
      - После `initialize` клиент получает события всех тредов уведомлениями `event`.
      - Ошибки сверх JSON-RPC: нет такого открытого треда, идёт ход, тред не стартовал (сервер, профиль), журнал правок отказал.
      - Добавлено после первой живой работы владельца:
        - `turn/edit` — сообщение хода, написанное заново. Разговор возвращается к началу этого хода, новое событие `thread_rewound` называет первый ход, ушедший из разговора, и ход начинается с новым сообщением.
          - Что откатанные ходы сделали с файлами, остаётся непросмотренным, и модель узнаёт об этом из того же сообщения.
          - Ход, перед которым была `/clear` или компакция, в разговоре уже не найти: ошибка `-32006`.
          - Тред сам ведёт номера ходов, которые остались в разговоре. Возобновлённый тред восстанавливает их по событиям хранилища, ходы из `chat` дописываются в конец.
          - Последние из этих номеров соответствуют сообщениям пользователя в истории агента, по одному на ход, поэтому `/clear` и компакция учтены сами собой.
        - `thread/delete` удаляет сессию с сессиями её субагентов, событиями и журналом правок. Открытую ядро сначала закрывает; сессию с идущим ходом не удаляет.
        - Режим треда (§8; 2026-11-10, по просьбе владельца).
          - `thread/start` и `thread/resume` принимают `mode`, без него — `edit_automatically`. Режим возвращается в `Opened` и в списке тредов для открытых.
          - `thread/mode` переключает режим открытого треда, в том числе во время хода: он действует со следующего вызова агента и его субагентов.
          - Событие `mode_changed` приходит всем клиентам при каждом открытии треда и при каждом переключении, поэтому последнее такое событие в сохранённом потоке — режим сейчас.
        - `call_draft` (2026-11-10) — вызов, который модель ещё пишет, для живого показа:
          - номер генерации и место вызова в ней;
          - инструмент по имени Claude Code;
          - аргумент по имени ognivo (`path`, `content`, `old`, `new`, `patch`, `command`…) и добавленный к нему текст.

          Как и дельты, он не хранится. Элемент вызова начинается после конца генерации, по порядку вызовов. Если генерация ничего не исполнила, придёт элемент `void`.
        - Мост окна (`apps/desktop/core.js`) пропускает к ядру только методы из своего списка. Метод не из списка теперь сразу получает ошибку `-32601`, а не ждёт вечно. Тест протокола сверяет список с методами клиента: `thread/mode` сначала в него не попал, и переключение режима молча не доходило до ядра.
    - **Тред** — сессия хранилища вида `chat`. Ядро ведёт её так же, как `ognivo chat`: тот же `connect`, правила, журнал правок. У каждого треда своя задача tokio.
      - Пока идёт ход, тред принимает только остановку, «ответить сейчас» и закрытие; на остальное отвечает «идёт ход».
      - Между ходами доступны Changes, accept и revert. Revert файла, изменённого ещё и чем-то другим, требует `force`.
      - Файлы инструкций разговора становятся первым элементом его следующего хода.
    - **Подтверждения — запросы ядра к клиентам** (`approval/ask`).
      - Вопрос получают все клиенты, в том числе подключившиеся, пока он ждёт. Засчитывается первый ответ, остальным уходит `$/cancelRequest`. Его же получают, когда вопрос снят: ход остановили.
      - В вопросе есть тред и элемент `approval` в потоке, у субагента — в его собственном треде. Проектор находит элемент по тому, кто спрашивает, инструменту и действию.
      - `allow_session` разрешает ровно это действие до конца сессии, как `a` в chat, а `deny` может нести, что делать вместо.
      - Доверие к allow-правилам проекта спрашивается так же (`rules/trust`), при старте треда. Ответ хранится, пока правила не изменятся.
    - **Повтор по `seq`.**
      - Ядро нумерует поток и пишет каждое событие, кроме текстовых дельт, в таблицу `wire` хранилища (§11): тред, тред пользователя, к которому он относится, JSON события.
      - `thread/read` отдаёт события треда и его субагентов после данного `seq`. Клиент, вернувшийся или открывший тред позже, читает пропущенное там, а событие, которое у него уже есть, не применяет второй раз.
      - Тред, у которого событий в хранилище нет (сессия `chat` или из времени до ядра), клиент читает как траекторию ATIF (`thread/trajectory`). Ядро при возобновлении продолжает нумерацию ходов, элементов и генераций с того, что есть в хранилище.
    - **Проверено.**
      - Интеграционные тесты (`crates/ognivo-cli/tests/core.rs`, настоящий сокет, поддельный llama-server):
        - старт треда, ход с записью файла и командой, вопрос и ответ, снятие вопроса у остальных;
        - Changes, revert и accept;
        - второй клиент читает ровно то, что первый получил, кроме дельт;
        - остановка хода, и модель узнаёт о ней со следующим сообщением;
        - закрытие тредов и выход ядра без клиентов;
        - вопрос о доверии правилам;
        - SIGTERM: тред сохранён и виден новому ядру.
      - Сквозной тест GUI (`apps/desktop/tests/core.spec.ts`, Playwright в настоящем окне) — см. §10.

## 4. Серверы и роутер

Агент не владеет серверами (решение 4). Поэтому ему нужны **определение возможностей** и **доктор**.

### Endpoint

Endpoint — это URL (`http://…` или `unix://…`), необязательный API-ключ и тип: `llama-server`, `ik_llama`, `llama-router`. При подключении и периодически ядро:
- опрашивает `/health`, `/props` (build_info, chat_template, n_ctx, total_slots, сэмплинг по умолчанию), `/v1/models` и `/slots`, если доступен;
- определяет семейство пробами `/tokenize`: `<|channel|>` → 200005 = Harmony; `<|tool_call>` → 48 = Gemma 4; `<tool_call>` → 248058 = Qwen3.5/3.8;
- снимает отпечаток шаблона (sha256) и сравнивает его с выверенными версиями из профиля;
- строит **caps** — модель возможностей:
  - промпт массивом токенов;
  - полнота ID токенов в стриме (см. §5.4);
  - `grammar_lazy` и `grammar_triggers`;
  - поля reasoning-budget;
  - `--swa-full` и чекпоинты;
  - число слотов и `--kv-unified`.

### Минимальные версии

«b3000+» не подходит: такие сборки не загрузят ни одну из трёх моделей. Практические минимумы upstream (номер сборки = номер коммита):
- `--jinja` — b4524;
- ленивые грамматики и tool calls — b4599;
- **gpt-oss — b6096** (2025-08-05);
- **Qwen3.5/3.8 (`qwen35`) — b7973** (2026-02-09);
- **Gemma 4 — b8637** (2026-04-02), плюс фиксы до осени 2026.

Профиль `verified` требует известную сборку и шаблон, остальное работает в деградированном режиме с предупреждениями. Для собственного сервера владельца рекомендуется сборка ≥ b11681 (локальный пин 2026-10-16) с патчем PR #31244 (§5.4).

**ik_llama.cpp** (локальный чекаут 2026-10-18, проверено в M0, `docs/m0/measurements.md`):
- архитектуры gpt-oss, gemma4 и qwen35 есть;
- работают: tool calling через OpenAI API, ленивые грамматики, `logit_bias`, `/slots`;
- **ID токенов в стриме не отдаёт вовсе**, `n_probs` их тоже не даёт;
- `/tokenize` распознаёт служебные токены даже при `parse_special=false`;
- в `/props` нет `build_info`.

Отсюда три класса серверов в caps:
- **A** — upstream с фиксом #31244: полноценный Native-путь;
- **B** — upstream без фикса: Native-путь, потерянные ID ставятся обратно по тексту следующего чанка и словарю (§5.4);
- **C** — ik_llama.cpp: полноценный путь Generic, Native только в урезанном режиме, всегда через ретокенизацию.

### Доктор

Проверяет n_ctx на соответствие бюджету профиля, число слотов и `--kv-unified`, версию сборки и вариант шаблона.
- Для известных моделей показывает рекомендуемую команду запуска (копируется кнопкой). Сам ничего не запускает.
- Явно предупреждает об опасных настройках:
  - квантованный KV ниже q8_0;
  - `--context-shift`;
  - шаблон из GGUF, который расходится с каноническим.

### Роутер

Роутер встроен в ядро:
- реестр endpoint'ов и соответствие модель → endpoint → профиль;
- **очередь к слотам**: сервер генерирует одновременно для стольких запросов, сколько у него слотов, и каждый шаг генерации агента или субагента ждёт своей очереди;
- очередь с приоритетами: основной агент > интерактивные запросы > субагенты > служебные задачи;
- учёт здоровья серверов.

Режим роутера самого llama-server (`--models-dir`, `--models-preset`, `/models/load|unload`) поддерживается как тип endpoint'а: модель указывается в каждом запросе (`"model"` в теле POST, `?model=` в GET), а `/health` у роутера свой.

- M2 (`ognivo_models::router`):
  - **Endpoint** — модель на сервере (у роутера llama-server — модель за ним), её профиль и число слотов из `/props` (`total_slots`).
  - **Аренда — очередь, а не место.** Каждый шаг генерации берёт один из слотов сервера на время своего потока (`Scheduled`). Когда заняты все, освободившийся слот получает старший приоритет, а внутри приоритета — тот, кто попросил раньше. Кто устал ждать (отменил шаг), уходит из очереди. Основной агент не ждёт: без свободного слота его шаг всё равно идёт, а сервер ставит его в свою очередь. Без известного числа слотов не ждёт никто.
  - **Запрос не закрепляется за слотом** (`id_slot` не передаётся, если не задан `--slot`). Кеш промптов llama-server держит состояние каждого разговора в RAM (`--cache-ram`, по умолчанию 8 ГиБ) и возвращает его в тот слот, куда разговор пришёл. А с `--kv-unified` слот, который простаивает, когда другой начинает работу, сохраняется в RAM и очищается. Запрос, закреплённый за очищенным слотом, начинает с нуля: сервер ищет кеш только для незакреплённого (b11924, `get_available_slot`: доля сохранённого у пустого слота — 0/0, и проверка «теряем больше половины» не срабатывает). Замер 2026-11-03 на CPU-роутере, gpt-oss-20b, `-np 2 --kv-unified`: основной разговор, к которому вернулись после чужого, взял из кеша 0 из 486 токенов с закреплением и 559 из 564 без него. Две сессии ognivo с закреплёнными слотами 0 и 1 обе считали промпт заново (0 из 727). Сессия без закрепления после них взяла 722 из 727. Ровно этот случай — основной агент простаивает, пока работает субагент, — закрепление и должно было спасать.
  - **Между процессами.** Аренда блокирует файл `<data>/slots/<сервер>-<слот>.lock` (flock), так что сессии ognivo на одном сервере делят его слоты, а упавший процесс отпускает свои.
  - **Здоровье.** `/health` сервера. У модели роутера — её статус в `/models`: loaded, loading, unloaded или sleeping (запрос её разбудит). Очередь сначала пробует здоровые серверы. `Router::watch` проверяет их периодически, для GUI.
  - **Роутер llama-server.** Модель — `--model` (id или алиас), иначе единственная модель профиля (подсказки имени ищутся в id, алиасах и имени GGUF), иначе единственная загруженная. Незагруженную ognivo просит загрузить (`/models/load`) и ждёт до 10 минут. Сервер ognivo не запускает (решение 4): загружает уже запущенный роутер, как он загрузил бы её по первому запросу. `doctor` показывает модели роутера с их профилями, а с `--model` проверяет одну как отдельный сервер.
  - Проверено вживую на CPU (`CUDA_VISIBLE_DEVICES=`) с роутером закреплённой сборки: `doctor` без модели и с ней, загрузка по запросу, Native-путь через роутер, две сессии одновременно.
  - Чего ещё нет. Несколько endpoint'ов задаются только в коде: CLI берёт один `--url`. Приоритет решает, чей шаг пойдёт следующим, но не прерывает уже идущий.

**LiteLLM не поддерживаем как основной путь.** Он нормализует запросы к OpenAI-формату. Теряются `/completion` с токенами, `/tokenize`, `id_slot`, грамматики, `/props`, то есть всё, на чём держится идеальная работа под конкретную модель. Допустим только как «глупый» upstream для Generic-профиля.

### Сэмплинг и сессия

- Сэмплинг всегда передаётся явно в каждом запросе. Дефолты llama-server (temp 0.8, top_k 40, min_p 0.05) не совпадают с рекомендациями ни одной из моделей.
- Сессия привязана к одной модели. «Продолжить другой моделью» — это форк со структурным саммари и показанной ценой пересчёта.

## 5. Слой моделей (ядро «идеальности»)

### 5.1. Пять слоёв

1. **TokenEngine** — бэкенд на уровне токенов.
   - Метод: `complete(prompt_ids, SamplerSpec, Option<CompiledConstraint>, SlotLease, StopSpec) → stream<TokenEvent>`, плюс `cancel`, `tokenize`, `caps()`.
   - Реализации:
     - `LlamaServerRaw` — `/completion`;
     - `Replay` — кассеты для тестов;
     - позже — собственный движок (например, cforge) как ещё одна реализация, без изменений в кодеках.
2. **Codec** — формат семейства, собранный из «китов»:
   - китов шесть: TurnKit, ReasoningKit, DeclKit, CallKit, ResultKit, ContentTokenizer;
   - методы: `render_prefix`, `render_item`, `gen_prompt`, `parser()`, `seal()`, `placement()`, `constraint() → Grammar IR`;
   - кодек чистый и детерминированный, у него есть semver, версия пишется в транскрипт.
3. **ToolProjector** — у каждой модели свои имена, формы и размещение инструментов, с переупаковкой аргументов в обе стороны.
   - Канонические ID в стиле Claude Code (`Bash`, `Read`, `Edit`, `Write`, `Grep`, `Glob`, `mcp__srv__tool`) используются только для хуков, разрешений и аудита.
   - Одна нормализация JSON Schema даёт три вещи: декларацию в синтаксисе модели, Grammar IR и обратный маппинг для валидации по исходной схеме.
4. **Policies** — данные (TOML) с provenance: на каждое значение — id eval-прогона, дельта и дата.
   - Что задаётся политиками: удержание reasoning, компакция, лестница ремонта, детектор петель, бюджеты, сэмплинг по классам запросов (main / retry / utility / summary), известные причуды модели.
5. **ModelDriver** — один шов для агентного цикла. За ним две реализации: `ChatCompletionsDriver` (Generic, M1) и `NativeDriver<Codec, TokenEngine>` (M2+). Цикл не знает, какой транспорт под ним.

### 5.2. Два пути

- **Generic** (`/v1/chat/completions`, M1) — базовая линия и путь для моделей без кодека. Агент не может подменить шаблон на чужом сервере. Чтобы этот путь работал правильно, нужно:
  - дословно возвращать `reasoning_content` в ассистентских сообщениях с `tool_calls`. Без этого у gpt-oss 7 из 120 ходов с битыми заголовками, с ним — 0 из 120 (issue llama.cpp #27720);
  - один повтор с новым seed при HTTP 500 «does not match the expected format»;
  - отслеживать `finish_reason=length` (обрезанный вызов не исполняется);
  - передавать `tool_choice` только строкой;
  - никогда не смешивать tools и response_format;
  - санитайзить спец-строки (§5.3).
- **Native** (`/completion` с массивом токенов, M2+) — основной путь для трёх профилей.
  - Агент сам рендерит промпт и сам разбирает поток ID токенов.
  - Строит свои грамматики и сам управляет бюджетом мышления.
  - Сгенерированные токены вставляет в следующий промпт по правилам `seal()`.
  - От шаблона, загруженного в сервер, этот путь не зависит, поэтому подходит для «любого сервера».
  - M2, начат 2026-11-03. Рендер Harmony (`ognivo_models::harmony`) повторяет эталонную реализацию openai/harmony 0.0.8 (Apache-2.0) до символа, вместе с её преобразованием JSON Schema в TypeScript: на этой форме модель и обучали.
    - Промпт — это куски «служебный id | текст содержимого». Текст токенизируется отдельно и без разбора спецтокенов (§5.3).
    - Куски не сливаются: эталон токенизирует каждый отдельно, и id на стыках от этого зависят.
    - Тест сверяет рендер сценария `seq` с эталоном M0 (`profiles/templates/gpt-oss-20b/golden`) байт в байт, а служебные id — по порядку.
  - Разбор вывода (`harmony::parse`) идёт по токенам. Служебные читаются по id, остальное — байтами, так что текст, который только выглядит как служебный токен, остаётся текстом. Разбор принимает:
    - оба порядка заголовка;
    - тип содержимого после `<|constrain|>`, склеенный с получателем или простым словом (` json`);
    - заголовок без `<|start|>`;
    - сообщение, налезшее на следующий заголовок (запись из штампа A M1).
  - Мусорные заголовки. Девять форм из llama.cpp #27720 — реальный вывод gpt-oss-20b, на котором парсер llama.cpp роняет весь ход. Здесь такой заголовок становится сообщением «мусор»: оно показывается как рассуждение и не исполняется, а следующее сообщение читается как обычно.
  - Чтение останавливается на `<|call|>` и `<|return|>`, а также после конца вызова или ответа, чем бы он ни кончился. gpt-oss делает один вызов за генерацию, а продолжение после ответа не нужно.
  - Аргументы вызова читаются так, как их пишет gpt-oss: первое JSON-значение, а если нужно — без ограды кода, без массива из одного элемента и без JSON-строки вокруг объекта. Каждый ремонт записан, потому что после ремонта сегмент рендерится канонически (§5.4).
  - Тесты режут каждый пример на токены по 1, 2, 3, 5 и 64 байта, в том числе посреди символов UTF-8. Разбор и поток событий при этом должны совпасть.
  - Native-драйвер (`NativeDriver`; `ognivo chat --native`, `t2 --native`). Промпт шага — история в Harmony:
    - системное сообщение — собственное у gpt-oss, с днём начала сессии и её уровнем рассуждения. Системные тексты истории становятся инструкциями developer, инструменты — его пространством `functions`;
    - анализ до последнего финального ответа выбрасывается (правило OpenAI). После него сообщения модели уходят обратно теми id, которые она сгенерировала, и каждый промпт продолжает предыдущий токен в токен (`seal()`, §5.4). Сообщение, чьи id не читаются обратно в него же, рендерится как в эталоне;
    - каждый текст содержимого токенизируется отдельно и без разбора спецтокенов, после разреза охраняемых строк (§5.3). Все новые тексты шага уходят одним запросом `/tokenize` со смешанным массивом, а уже знакомые берутся из памяти драйвера: история повторяется каждый шаг.
  - Байты сгенерированных id берутся из словаря сервера: `/tokenize` с массивом id и `with_pieces` отдаёт куски словаря, а неполный UTF-8 — байтами. Своего токенизатора ognivo для этого не нужно.
    - Словарь (все id ниже служебных) драйвер забирает целиком, пока сервер читает промпт первого шага: частями по 16 384 id, по 8 запросов сразу. Сессии и субагенты одного процесса на том же сервере и модели делят его.
    - Раньше байты новых id спрашивались по мере появления, по запросу на кусок потока. На удалённом сервере каждый запрос стоил два круга по сети, и ход ждал этого ~20–30 с при генерации за 2 с (2026-11-08: сервер в 0,25 с пути, 38 запросов на ход). Весь словарь Qwen3.8 — 7,9 МБ: локально 0,1 с, на том сервере 5,7 с, один раз.
    - Если сервер словарь не отдал, драйвер спрашивает байты по мере появления, как раньше, и пробует снова через минуту.
  - Id, которые поток потерял, ставятся обратно по тексту следующего чанка и словарю (§5.4). Шаг падает, только если текст их не показывает.
  - Раскладка инструментов A (`--priors`, `projection::Layout::Priors`). gpt-oss получает инструменты своего обучения:
    - `container.exec` со списком аргументов;
    - `repo_browser.open_file`, `search`, `print_tree` и `apply_patch`.
  - Они объявлены как встроенные пространства в системном сообщении и отображаются на те же вызовы ognivo, а системный промпт называет их. Раскладка B — прежние `functions`.
  - Грамматика вызова просыпается на `to=` любого объявленного пространства (§5.7).
  - apply_patch (крейт `ognivo-patch`). Разбор V4A и нечёткий поиск строк взяты из OpenAI Codex (`codex-rs/apply-patch` на b127a3643, Apache-2.0; LICENSE и NOTICE в крейте), применение работает над текстом.
    - Инструмент планирует все файлы патча до первой записи: патч применяется целиком или никак.
    - Он спрашивает одно разрешение на все файлы и пишет каждый через журнал правок. Ответ — сводка Codex («Success. Updated the following files:»).
    - Удаление и перенос файлов идут через shell: журнал пока не умеет «файла нет».
    - Вызов apply_patch через shell (`apply_patch <<'EOF' … EOF`, а также `applypatch` и `repo_browser.apply_patch`) и с патчем аргументом — тот же патч: так его вызывал Codex, и gpt-oss это выучила. В первом прогоне раскладки A так было написано 17 патчей из 34, четыре из них без закрывающего маркера, и bash читает такой heredoc до конца. Если после heredoc есть ещё команды, это обычная команда shell.
    - Текст отказа без пользователя называет то, чем менять файлы в этой раскладке: apply_patch, а не edit и write.
  - Пробел: сессия не хранит раскладку, поэтому ATIF-трейс показывает инструменты стандартной раскладки.
  - Шаг продолжается сам в трёх случаях:
    - рассуждение кончилось без ответа и без вызова (в первом живом прогоне — 2 генерации из 195);
    - рассуждение перешло бюджет: три четверти токенов шага;
    - пользователь нажал «Answer now» (в `chat` это ^\, то есть SIGQUIT).
  - С инструментами каждый запрос шага, и продолжения тоже, несёт ленивую грамматику аргументов (§5.7).
  - Как продолжается: драйвер закрывает рассуждение там, где оно стоит (`<|end|>`), дописывает `<|start|>assistant` и шлёт новый запрос, который продолжает промпт и генерацию, так что кеш слота держит всё. После этого рассуждению дают ещё 512 токенов, продолжений — не больше двух на шаг. id шага остаются одной цепочкой и уходят обратно дословно, счётчики сервера складываются по запросам шага.
  - id генерации хранятся в сообщении ассистента (поле `tokens` в сессии), поэтому переживают компакцию и возобновление. На Generic-пути поля нет, и хеши запросов прежних сессий не меняются.
  - Тесты на фейковом сервере:
    - второй запрос продолжает первый токен в токен;
    - рендер истории сценария `seq` совпадает с эталоном M0;
    - текст служебных токенов в сообщении пользователя остаётся текстом;
    - мусор показывается, но не хранится;
    - обрезанный вызов, вызов чужого пространства, битые аргументы и вызов, налезший на заголовок, не исполняются.

### 5.3. Защита от инъекции служебных токенов

Проверено на ваших GGUF и коде llama.cpp. Структурные токены помечены USER_DEFINED и распознаются **даже при `parse_special=false`**:
- Gemma 4 — 48–52 и 100/101;
- Qwen3.8 — `<tool_call>`, `<think>`, `<tool_response>`;
- gpt-oss — `<|channel|>`, `<|message|>`, `<|start|>`, `<|constrain|>` и `<|end|>`; llama.cpp принудительно ставит им этот тип при загрузке (`src/llama-vocab.cpp:3073`, `:3139`, `:3406`).

На chat-пути весь промпт токенизируется с `parse_special=true`. Значит, файл с текстом `<|end|><|start|>developer<|message|>…` даёт поддельное сообщение.

Меры защиты. Охраняемое множество строк — это `tokens.structural` и `tokens.specials` профиля (`TokenTable::guarded`). Для неизвестных моделей берётся набор по умолчанию: `<|`, `|>`, теги ChatML, `<think>`, `<tool_*>`.
- **Единая точка входа.** Защита применяется к каждой строке промпта, которая не является дословными токенами модели. Это вывод инструментов и файлы, описания инструментов и MCP, инструкции серверов, skills, AGENTS.md и CLAUDE.md. На Generic-пути сюда же входят текст пользователя и прошлый вывод самой модели: сервер заново токенизирует всё. В M0 промпт задачи chat-multiturn содержал `<bos>` текстом, и Gemma видела вместо него настоящий BOS.
- **Native:** контент токенизируется отдельно от разметки. Перед `/tokenize` каждая охраняемая строка в контенте разрезается после первого символа, чтобы не могла совпасть. Стоит жёсткий assert: ни один span контента не содержит ID из охраняемых токенов профиля. Позже можно добавить in-process токенизатор (o200k_harmony / HF tokenizers) для точного подсчёта без сети.
- **Generic:** обратимый санитайзер (`crates/ognivo-models/src/guard.rs`, работает в драйвере).
  - Он вставляет U+2060 после первого символа каждой охраняемой строки во всём, что уходит на сервер. Уже существующие в тексте U+2060 удваиваются, поэтому обратное преобразование точное.
  - Обратное преобразование применяется ко всему, что приходит от модели: к тексту, рассуждению и аргументам всех инструментов (в JSON — по строкам). Модель может скопировать строку с U+2060 или без него: инструменты в обоих случаях получают исходный текст.
  - Модель не всегда копирует сам U+2060. На T2-mini gpt-oss написал вместо него U+200D ZERO WIDTH JOINER, а Qwen, когда пыталась записать U+2060 нарочно, писала U+2063 INVISIBLE SEPARATOR. Поэтому охраняемая строка, разорванная после первого символа серией невидимых символов форматирования (U+200B, U+200C, U+200D, U+FEFF, U+2060 и соседние с ним U+2061–U+2064), тоже возвращается целой (`Guard::restore`). В остальном тексте эти символы остаются: у эмодзи-последовательностей их ZWJ на месте.
  - Объяснять этот приём в системном промпте не нужно: это проверено и отменено. Модели бывает принимают верный файл за ошибку. В первом прогоне трёх моделей 2026-11-02 Gemma и Qwen записали верный текст, не нашли U+2060 в выводе `od`/`hexdump` и потратили остаток шагов на попытки его вставить. Строка «копируй как видишь, в файлах U+2060 не будет» сделала хуже. Qwen стала сразу писать токен разметки без U+2060, защита отвергала вызов, и сценарий с ним у неё упал с 3 из 3 до 1 из 3. Gemma продолжала искать U+2060 в байтах. По итогу токенных сценариев строка от разброса не отличается: с ней 14 из 18, без неё 16 и 14 в двух замерах. Отменило её то, что Qwen сразу стала писать токен разметки без U+2060. Как писать такой текст, модель узнаёт из записки к отвергнутому вызову, в тот момент, когда это нужно. Сам провал на Generic-пути неустраним: модель видит U+2060 и в задании. Его убирает Native-путь.
  - Строка разметки сообщений и вызовов своей модели (`tokens.framing`), пришедшая в аргументах без U+2060, — это не копия, а утечка формата: модель вышла за конец вызова. По правилу §5.4 такой вызов не исполняется (Malformed). В штампе A M1 так было трижды: gpt-oss записал в тест заголовки следующего сообщения, Gemma дважды записала в файл конец канала мысли и заголовок нового вызова. Теги рассуждения (`<think>` у Qwen, канал мысли у Gemma) в `framing` не входят: задачи их цитируют. На всех 1555 записанных вызовах M0 и штампа A правило срабатывает ровно на этих трёх, а запись `<think>` в chat-multiturn у Qwen проходит. Чтобы написать строку разметки намеренно, модель ставит `\u2060` после первого символа.
  - Полнота множества проверена по словарям GGUF (2026-10-31): профили покрывают все токены CONTROL и USER_DEFINED трёх моделей, у gpt-oss — вместе с 11 `<|reserved_N|>`. По построению после экранирования в тексте не остаётся ни одной охраняемой строки, а токенизатор сопоставляет спецтокены только по точному тексту.
- **Правило репозитория:** не писать литералы спец-токенов слитно в исходниках и тестах самого ognivo. Тогда агент может работать над собой.

### 5.4. Инварианты Native-пути

Найдены при проверке кода:
- **Потоковый `/completion` теряет ID токенов**, на которых UTF-8 ещё неполон. В M0 на старой сборке из 72 ID потерялось 15. Исправление — PR #31244 (открыт 2026-10-27); в нашей сборке с ним доходят все 72.
  - Порядок действий: сверяем число ID с `timings.predicted_n`.
  - Если не совпало — восстанавливаем (ниже). `n_probs` не помогает: там ID теряются так же (проверено в M0). Расхождение KV тогда дешёвое: откат идёт к чекпоинту на конце прошлого промпта.
  - EOG-токен приходит последним ID потока, его текст в `content` не входит.
  - Аргументы инструментов собираем из байтов токенов, а не из `content`.
  - 2026-11-03, сборка с PR #31244, gpt-oss-20b на GPU, `-np 2`: два субагента из четырёх упали на финальном ответе с «the server streamed 897 of 902 token ids» и «770 of 773».
    - В их ответах, прочитанных по ID, ровно 5 и 3 символа U+FFFD: на каждом многобайтовом символе (U+202F, U+2011) потерян один ID.
    - Текст сервера в `content` был цел. На CPU с теми же флагами и двумя параллельными потоками потери не воспроизвелись: 700 из 700 ID, 154 и 98 многобайтовых символов.
    - Теперь шаг с такой потерей не падает:
      - содержимое сообщений, не прочитанное как UTF-8, чинится по тексту сервера: каждая серия U+FFFD заменяется многобайтовым символом, который стоит там у сервера;
      - ID генерации назад не идут: сообщение рендерится из текста, и кеш сервера служит разговору до него.
    - Если починенное сообщение не стоит целиком в тексте сервера, это значит, что пропал кусок, который читатель мог бы декодировать. Такой шаг по-прежнему ошибка. Ошибка и тогда, когда ID больше, чем сервер насчитал.
  - 2026-11-08, Qwen3.8 на удалённом сервере upstream (класс B): каждый из пяти ходов сессии упал, потеряно от 1 до 19 id из 6–14,5 тыс. за шаг.
    - Как теряет upstream: после id, на котором UTF-8 неполон, чанка нет вовсе. Следующий чанк несёт весь текст с прошлого и только свой id.
    - Почему не помогла починка по тексту: у Qwen3.8 потерянный id начинается с пробела. « ⊕» — это « \xE2\x8A» и «\x95», « ≡», « ✗», « ρ» и « ⟺» устроены так же. Вместе с первым байтом символа терялся пробел, и починка, ставившая на место U+FFFD ровно один символ, не находила сообщение в тексте сервера.
    - Теперь (`put_back`): текст чанка ложится поверх байтов его id, а у сервера класса A — ещё и поверх id, чей текст не пришёл. Лишнее впереди — байты потерянных id. Их id — наименьшее число id словаря, чьи куски дают эти байты, длинные вперёд.
      - Проверка на словаре Qwen3.8 с 8080: 3328 символов из 24 блоков Юникода, после пробела, буквы, цифры, скобки и перевода строки. Поток смоделирован, как его режет upstream. Из 15 678 потерь все восстановлены теми же id, что дал токенизатор.
      - Если id вышло меньше, чем насчитал сервер, текст всё равно верен (это байты сервера), но id назад не идут.
    - Чанк с управляющим токеном не раскладывается: его текст в `content` может быть, а может и не быть. Починка по тексту (`laid`) теперь допускает до 8 целых символов перед многобайтовым: те, что потерянный id нёс с собой.
- **Ленивая грамматика сопоставляется начиная с текста триггера** (проверено в M0). Поэтому каждая GBNF начинается с самого триггера: Gemma — `<[48]>`, gpt-oss — заголовок вызова, Qwen — `<tool_call>`.
- **Серверный reasoning-budget не видит префилл мысли** в tool-шагах Gemma. Поэтому бюджет мышления и кнопка «Answer now» реализуются на стороне агента: отменить стрим, дописать конец мысли (Gemma `<channel|>`, gpt-oss `<|end|><|start|>assistant`) и продолжить. Для gpt-oss так и сделано (M2, §5.2).
- **На `/completion` SWA-чекпоинты создаются только у конца промпта.** Поэтому плановые точки расхождения (начало хода, конец статического префикса) должны совпадать с концом одного из прошлых запросов («якорные» запросы).
- **`seal()`.** Чистый разбор вставляется дословно. После ремонта L1 сегмент рендерится канонически: модели нельзя показывать её же дрейф. L2 — salvage: обрезать по последней корректной границе и продолжить под грамматикой с принудительным префиксом (gpt-oss: `<|start|>assistant<|channel|>commentary to=functions.`; Gemma: `<|tool_call>call:`).
- **logit_bias = −inf** для токенов, которые модель не должна генерировать. Управляющий токен или невалидный UTF-8 внутри аргумента — ошибка формата, такой вызов не исполняется.
- **BOS:** у Gemma агент ставит его сам (id 2); у gpt-oss BOS не ставится.

- **Qwen3.8 на Native-пути (M3).** Драйвер общий для форматов: `Format::Harmony` и `Format::Qwen`, у каждого свой читатель (`AnyReader`). Токенизация по частям, продолжение шага, починка потерянных ID и защита от повторов — общие.
  - Промпт — отрисовка шаблона (`ognivo_models::qwen::render`). Эталонный тест сверяет её символ в символ с отрисовкой `evals/templates/scenarios/seq.json` в HF transformers (`profiles/templates/Qwen3.8-27B/golden`).
  - Служебные токены идут по ID: `<|im_start|>` 248045, `<|im_end|>` 248046, `<tool_call>` 248058, `<think>` 248068 и другие (`tokenizer.ggml.tokens` в GGUF; всё от 248044 — служебное). `<tool_call>`, `<think>` и `<tool_response>` — user_defined, llama.cpp находит их в тексте и без разбора служебных, поэтому содержимое режется по ним, как у gpt-oss.
  - Текст между двумя служебными токенами токенизируется одним куском, текст шаблона и содержимое вместе: так токенизирует эталон. В самом тексте шаблона тоже стоят служебные `<tool_call>` — в описании формата.
  - Прошлые рассуждения остаются все, как у шаблона по умолчанию (`preserve_thinking`). Сообщения модели идут назад её же ID, если читаются в то же сообщение. В конце всегда `<|im_end|>`, после него `\n`. Остальное рисуется шаблоном.
  - Читатель терпим, как разборщик llama.cpp (`common/parsers/qwen3-coder.cpp`). Рассуждение может кончиться на `<tool_call>` без `</think>`. Значение параметра — текст до первого `\n</parameter>`: строка, если схема её допускает, JSON, если нет. Вызовов в генерации может быть несколько. Вызов без переводов строк или без `</tool_call>` читается, но его ID назад не идут.
  - Грамматика — та, что строит llama.cpp на Generic-пути: ленивая, будится токеном `<tool_call>`. Функция из объявленных, обязательные параметры в любом порядке (до трёх; больше — в порядке схемы), затем необязательные. Строковое значение задаётся правилом «текст без `\n</parameter>\n`», построенным автоматом Кнута — Морриса — Пратта.
  - Бюджет рассуждения и «Answer now» закрывают рассуждение так, как его закрывает шаблон: `\n</think>\n\n`. Уровни — `xhigh`, `medium`, `low` и `off`; при `off` генерация начинается после пустого блока рассуждения. BOS у Qwen не ставится.
  - Замер T2 2026-11-05 (коммит 0b36439, seed 1–3, 19 мин): прошли 102 из 102. parse_ok и schema_ok — 100%, правка с первой попытки — 100% (36 из 36). На Generic-пути в тот же день было 102 из 102, 94,6% и 24 мин. `arguments-write-framing-token` прошёл 3 из 3: Native-пути не нужен U+2060.
  - Cache hit на Native-пути — 65,2%, на Generic-пути — 82,4%. Причина в llama.cpp. Контрольные точки гибридной модели в начале сообщений пользователя сервер ставит по границам сообщений, а границы знает только chat-путь: `/completion` получает пустую сессию шаблона (`handle_completions_impl`). Остаются точки у конца промпта (`4 + n_ubatch` и 4 токена до конца). Внутри сессии их хватает: следующий шаг продолжает предыдущий. Новая сессия (прогон T2, субагент) заново считает системное сообщение с инструментами, как Generic-путь до `--checkpoint-min-step 512`.
  - Поправка (`NativeDriver::warm`): первый шаг новой сессии Qwen сначала шлёт одно системное сообщение (`/completion` без потока, `n_predict` 0, тот же слот), и точка встаёт у его конца. Сессия, которая продолжается, этого не делает: её история лежит на слоте, а запрос её бы обрезал. gpt-oss идёт с `--swa-full`, ему точки не нужны.
  - Замер T2 после поправки, 2026-11-05, коммит e40c4e3. На тех же 102 сценариях cache hit вырос с 65,2 до 84,3%, это выше Generic-пути (82,4%), а время упало с 19,0 до 17,6 мин. Прошли 101 из 102 (`loop-failing-build` 2 из 3). 45 прогонов `mcp` прошли все, `tool_correct` — 100% при 5, 15 и 40 инструментах. При 40 модель находила инструменты поиском и звала их по имени, с грамматикой по их схемам.

Если профиль не выбран, их сообщает модель, которую ядро нашло на сервере: метод `server/detect` ищет её так же, как старт треда. Уровень, которого у модели нет, не отправляется — тред получает уровень по умолчанию. Раньше форма для любой модели предлагала low/medium/high gpt-oss, и `high` для Qwen3.6 обрывал старт треда.
- **Native-путь в GUI** (2026-11-06). Форма треда предлагает Native-путь только моделям, чей формат он читает: gpt-oss и Qwen (`ognivo_models::native::reads`). Признак берётся из `profiles.json` (поле `native`) или из `server/detect`. У Gemma 4 галочка недоступна, и подпись говорит, что эта модель работает на Generic-пути. Тред, который открывается заново, тоже идёт на Native-пути, только если путь читает его модель. Раньше форма отправляла `native` любой модели, и для Gemma старт падал с ошибкой «the Native path reads gpt-oss's and Qwen's formats so far». Кодека Gemma пока нет (M3, §13). `profiles.json` пишет `npm run profiles` (apps/ui/scripts/profiles.mjs), а тест ognivo-models сверяет его с профилями: путь, уровни, контекст.

### 5.6. Контекст и KV-кеш

- **История только дописывается.** System, developer и tools неизменны в пределах сессии, дата у gpt-oss заморожена на старте.
- **В системном промпте нет ничего от проекта.** Путь проекта и файлы инструкций идут следующим сообщением, от пользователя: `[ognivo] The project is at …` (`ognivo_core::agent::project_context`). Поэтому все сессии одной модели с одной раскладкой и одним уровнем рассуждения (у gpt-oss — ещё и одного дня) начинаются одинаково: system, developer и tools. Слот отдаёт этот префикс из кеша новой сессии, разговору после `/clear` и сессии в другом проекте. У gpt-oss путь раньше стоял в начале developer, перед объявлениями инструментов, и первый шаг каждой сессии считал их заново. Компакция оставляет оба первых сообщения. Разговор, записанный до этого (путь и инструкции в system), продолжается как был. Шаблоны всех трёх моделей принимают два user-сообщения подряд: чередования ролей они не проверяют.
- **Чем проверить изменение.** Сообщение о проекте называет его файлы сборки и тестов: манифесты в корне (Cargo.toml, package.json, pyproject.toml, go.mod, Makefile и подобные), каталоги `tests/`, `test/`, скрипты build\*, test\*, check\* в корне и в `scripts/` (`ognivo_core::verify::project_checks`). Если ничего такого нет, сообщение так и говорит: сборкой изменение не проверить, перечитай изменённые строки и не пиши программ ради проверки. Неподтверждённый ответ тогда не отправляется назад со словами «запусти сборку». Почему: ни в одном из 34 сценариев T2 нет файла сборки, а промпт требовал запустить сборку. В пяти провалах Gemma (2026-11-03) это выглядело так: правка уже сделана, затем модель пишет test.rs, просит rustc, получает отказ и упирается в лимит шагов. Системный промпт теперь говорит «run the project's build or tests … if it has them».
- **Лимит шагов виден модели.** За два шага до лимита к последнему результату добавляется заметка: «2 steps of this turn are left. Finish now …», так же, как заметки о лимите времени. В петлях T2 Gemma знала ответ уже на 4-м шаге из 10, но искала дальше до лимита.
- **На лимите — ответ без инструментов.** Если шаги кончились, агент один раз просит ответ с `tool_choice: none`: «This turn has used all its N steps, so no more tools run. Give the final answer now …». Ход всё равно кончается `step_limit`, но с ответом: `TurnEnd::StepLimit(Some(answer))`, `turn_completed.answer`. Пользователь видит, что ход нашёл, а основной агент получает отчёт субагента («ran out of its N steps; asked then, it reported: …»). Вызовы, пришедшие вместо ответа, не выполняются и в историю не попадают. T2 такой ход по-прежнему не засчитывает: модель не остановилась сама. llama.cpp при `tool_choice: none` оставляет инструменты в шаблоне, поэтому префикс и кеш не меняются. Заметку о двух шагах Gemma 2026-11-05 пропустила. В `chat` лимит 200 шагов, и петля без этой меры тратит их все, не дав ответа.
- **Динамика** (git status, диагностика, план, «файлы изменены извне») размещается по `Codec::placement()`:
  - внутри tool-цикла — пристёгивается к следующему результату инструмента (у Gemma — доп. ключи в response-dict);
  - между ходами — в начало следующего user-сообщения;
  - mid-conversation system не используется: в обучении его не было.
- **Компакция посреди хода** — новая «эпоха» кеша, все меры одним пакетом. Состав: статический префикс → [исходная задача + структурное саммари + план + изменённые файлы и проверки] → последние N шагов дословно вместе с CoT.
  - Триггер у gpt-oss — по остатку контекста; у Gemma — по измеренному эффективному окну.
  - Саммари генерируется в форке основного слота.
  - M1 (`ognivo_core::compact`). Перед каждым шагом агент оценивает промпт: сколько токенов сервер держал после прошлого шага плюс новые сообщения из расчёта 3 байта на токен. Порог — рабочий контекст сессии × `compact_at` профиля, но не ближе к `n_ctx` слота (из `/props`), чем `max_tokens` шага плюс запрос саммари. Если в слоте меньше 8K сверх этого, решает только бюджет профиля.
  - **Рабочий контекст сессии** (2026-11-06, `compact::session`). По порядку:
    - то, что выбрал пользователь: `--context 128k` у `chat` и `run`, переменная `OGNIVO_CONTEXT` или поле Context в форме треда;
    - иначе окно слота сервера;
    - иначе `working_max` профиля.

    Окно, в котором компакции нет места (см. выше), рабочим контекстом не считается, и тогда действует бюджет профиля. Выше `ceiling` профиля контекст не поднимается. Это окно, на котором модель обучали, или меньше, если дальше она ломается: gpt-oss 128K, Gemma 4 256K, Qwen3.6 256K, Qwen3.8 256K (карточка модели). До 2026-11-08 у Qwen3.8 было 112K: за ~130K llama.cpp, по #27756, отдаёт мгновенный EOS, а сами мы это не мерили. Владелец решил дать 256K. Теперь шаг, в котором модель на контексте больше 64K не написала ничего, даже рассуждения, считается этим сбоем: история с этого места сжимается до `compact_at` от контекста сбоя, и шаг идёт снова. `working_max` профиля теперь значит «на чём профиль мерили»: в форме это число помечено так. На него же опирается предупреждение «the server's context leaves about … where the profile plans for …».
    - Почему: раньше контекст брался из профиля и от сервера не зависел. У Gemma это 64K, а сжатие начиналось на 65 %, около 42,6K, хотя сервер владельца держит 262 144 токена на слот. Теперь на том же сервере рабочий контекст 256K, а сжатие начинается около 170,4K.
    - `chat` пишет под шапкой строку: `context 256K (the server's window), compaction near 170.4K`. Источник там один из таких: «your choice», «the server's window», «the profile's: …»; потолок модели тоже назван, если он сработал. Та же строка приходит GUI в заметках старта.
    - `Opened.context` и `ThreadSummary.context` дают клиенту три числа: рабочий контекст, порог сжатия и окно слота. Композер считает сообщение против них, а не против бюджета профиля: «after it ≈ … of 256K (…) · compacts near 170k». `server/detect` сообщает окно, и форма предлагает размеры до окна и потолка модели, а под полем показывает порог сжатия.
    - Саммари пишет сама модель: тот же префикс, те же инструменты, тот же слот, `tool_choice: none`, в конце — просьба о сводке по форме Task / Done / Failed / Now / Next, не длиннее 400 слов. Сервер берёт историю из кеша: llama.cpp рендерит инструменты при любом `tool_choice`, `none` лишь отключает разбор вызовов.
    - Новая история: system → одно сообщение пользователя с запросами пользователя (последние 8, каждый до 2000 знаков), саммари и фактами ognivo (непросмотренные правки, команды с побочными эффектами, сборки и тесты хода по порядку, статус проверки, остаток лимита времени) → последние шаги хода дословно, с рассуждением: не больше 4 и не больше четверти порога, а не влезающий результат обрезается с пометкой.
    - Если саммари не пришло (вызов вместо текста, обрезка, пустой ответ), сообщение говорит об этом, а факты и шаги остаются. Компакция не делается, если сбросить можно меньше четверти промпта.
    - Компакция «пустая», если с прошлой агент не прочитал ни одного нового для хода файла и ничего не изменил. После двух пустых подряд ход останавливается: файлы, нужные работе, вместе в контекст не помещаются. Проверка на живом gpt-oss при `-c 32768` (порог 15.9K) без этого правила дала семь компакций подряд и ни одной правки: после каждой модель заново читала те же два файла. «Ничего не изменилось» само по себе признаком не служит: исследовательская задача законно только читает.
    - В том же прогоне запрос саммари взял из кеша 14430 из 14464 токенов истории, а первый шаг после компакции — весь статический префикс (666 токенов: system, инструкции и инструменты). Заново считаются только сообщение компакции и сохранённые шаги.
    - `chat` предупреждает под баннером, если `n_ctx` сервера оставляет разговору меньше, чем закладывает профиль.
    - После компакции детектор повторов начинается заново, файлы инструкций подкаталогов придут снова со следующим вызовом, а сессия начинает следующий разговор (§11). `chat` и `run` показывают начало и итог, в JSONL это события `compacting` и `compacted`.
- **Телеметрия на каждом шаге:** ожидаемый и фактический `cache_n`, причина промаха. Всё это видно в GUI.

### 5.7. Грамматики

- **Grammar IR** компилируется в GBNF (llama.cpp); позже — в Lark/llguidance и маски для собственного движка.
- **Ленивая активация** по триггеру вызова. Внутри reasoning грамматика выключена: «рассуждай свободно, ограничивай только вызов».
- **gpt-oss:** схема аргументов. M2 (`harmony::arguments_constraint`, правила из схем — `grammar`):
  - Грамматика начинает работать на `to=functions` в заголовке, в начале генерации или после `<|start|>assistant`, как собственные триггеры llama.cpp для gpt-oss. llama.cpp ищет триггер по всему написанному, служебные токены видны ему как текст, а грамматику кормит с первой группы захвата.
  - Дальше она пропускает только имя объявленной функции, остаток заголовка в любом порядке и аргументы по схеме функции, а после них — только конец генерации.
  - Схема даёт объект своих свойств в объявленном порядке (так и у конвертера llama.cpp). Необязательные можно пропустить, других ключей нет. Типы: строка, целое, число, логическое, null, enum, массив и вложенный объект; чего конвертер не знает, становится любым JSON-значением.
  - Рассуждение остаётся свободным, заголовок читает разбор.
  - Служебный токен внутри строки грамматика не останавливает: она видит его текст. Это ловит разбор.
  - Первая ступень держала только синтаксис JSON и просыпалась на `<|message|>`. В живом прогоне (3d84888) сбоев формата было 0 из 525, но 23 вызова из 432 звали несуществующие инструменты (`search`) или давали инструменту чужие ключи (`glob` у glob). На Generic их не пропускает грамматика сервера по схемам. С грамматикой по схемам schema_ok в живом прогоне — 100% (422 из 422), сбоев формата 0 из 515 (§11).
  - Проверено настоящим парсером llama.cpp (`test-gbnf-validator`, без модели) на грамматике инструментов gpt-oss. Девять правильных вызовов проходят: оба порядка заголовка, склеенный `constrain`, простой `json`, без типа, канал analysis, пропущенный необязательный ключ. Девять неправильных отвергаются: `search`, ключи `glob` и `limit` у glob, число строкой, пропущенный обязательный ключ, чужой порядок ключей, лишняя кавычка, текст после объекта, канал final.
  - Триггер проверен тестом: он срабатывает на заголовке вызова в обоих порядках и после мусорного заголовка, но не на тексте заголовка в рассуждении, не на `to=assistant` и не на чужих пространствах.
- **Gemma:** schema-aware GBNF в её DSL — llama.cpp этого не делает, поэтому делаем только если данные покажут, что syntax-only + валидация + один повтор не хватает. **Qwen:** XML-параметры.
- **Маски по именам инструментов** вместо правки массива tools («mask, don't remove»). Так работают режим plan и ограничения субагентов.
- **Свой компилятор JSON Schema → GBNF**: портируем `json-schema-to-grammar` с фиксом #25923 и фаззим на реальных MCP-схемах.

## 6. Агентный цикл и инструменты

- **Цикл:** generate → parse → validate (полная JSON Schema 2020-12) → policy/approval → execute → append → loop. Вызов исполняется только после закрытия вызова и EOG, никогда — по стрим-дельтам или после обрезки по `n_predict`.
- **Лестница ремонта:**
  - L0 — грамматика;
  - L1 — мягкий разбор по причудам семейства;
  - L2 — тихий salvage (мусор в трейс, не в контекст модели), не больше 2 раз;
  - L3 — видимая ошибка инструмента с подсказкой;
  - L4 — стоп и показ сырого вывода.
- **Петли и застой** (`ognivo-core/src/repeats.rs`):
  - Повтор — вызов с тем же отпечатком и тем же результатом, пока в проекте ничего не менялось. Отпечаток — инструмент, аргументы в терминах ognivo и рабочий каталог. Нового текста правки в нём нет: неприменившаяся правка падает одинаково, что бы она ни писала. В штампе A' M1 Gemma дважды подряд отправила один неверный old_string с разными заменами.
  - Изменение — применённая правка или запись либо любая команда, кроме только читающих. Вызов, который сам что-то меняет, повтором не бывает, а вызов, сделанный до изменения, после него повтором не считается. В M0 счётчик одинаковых вызовов OpenCode срабатывал на `cargo test` между правками. Между вызовами проект не меняется: всё, что команда оставила работать, завершается вместе с ней.
  - На 2-й раз результат помечается «unchanged». На 3-й вызов не исполняется, и модель получает альтернативы. 4-й раз останавливает ход, если после 3-го не было ничего нового, и дальше решает пользователь. Если новое было, 4-й раз пропускается, как 3-й.
  - Калибровка на записанных прогонах штампов A и A' (40 прогонов, 1141 вызов): пометка была бы 18 раз, пропуск 5–6 раз, остановка ни разу. Буквальное правило «на 4-й раз — стоп» остановило бы решённый прогон: gpt-oss на asusctl-armoury-attr-names четырежды возвращался к одному grep между новыми поисками.
  - Детектор опирается на то, что все прежние результаты лежат в истории. Поэтому компакция должна начинать его заново.
  - Отдельно — детектор отсутствия прогресса.
- **Ядро инструментов** (≤ ~10, проекции под модель): read (с номерами строк, постранично), edit, write, shell, search (ripgrep), glob, update_plan с периодической «рецитацией» в результатах, ask_user, а также skill и tool_search (§9).
- **После правки** — синтаксическая проверка через tree-sitter. Опционально — проектная команда проверки (`cargo check`, `tsc --noEmit`, `ruff`) после пачки правок, в результат идут только ошибки. LSP — после v1.
- **Скрытых LLM-вызовов в v1 нет.** Заголовок сессии — первая реплика, commit-сообщение — по кнопке и только при свободном слоте.

## 7. Субагенты (решение 16)

- **Вызов.** Оркестратор (по умолчанию gpt-oss-20b, effort high) вызывает инструмент `delegate{tasks}`: у каждой задачи title, goal, context, mode `read|write`, files. Каждый субагент получает свежий контекст (статический префикс + бриф), а каждый его шаг — очередь к слотам сервера (§4). Возвращает ограниченный по размеру структурированный отчёт: итог, находки, изменённые файлы, запущенные команды, статус. Отчёт приходит оркестратору как tool result, полный транскрипт хранится отдельно.
- **Изоляция записи в v1.** Субагенты в режиме `read` работают параллельно: исследование, анализ, ревью, тесты. Субагенты в режиме `write` берут **эксклюзивные блокировки** на объявленные файлы; правка вне них — ошибка; конфликтующие задачи выполняются последовательно. Git worktree на субагента — после v1.
- **Подтверждения.** Общий **inbox подтверждений** по всем сессиям и субагентам. Ждёт только тот агент, которому нужен ответ.
- **Ресурсы.** Модель одна на сервер. На 24 ГБ реально N = 2–4: суммарная скорость растёт, скорость отдельного агента падает (замерить в M0). Рекомендация для сервера: `-np N --kv-unified` с потолком контекста на слот.
- **Effort.** У gpt-oss он сидит в system-префиксе, так что effort субагента — это отдельный префикс. Субагенты работают на medium, служебные задачи — на low.
- M2 (`ognivo_core::agent::delegate`, флаг `--subagents` у `chat`, `run` и `t2`):
  - **`delegate{tasks}`.** Задача — title, goal, context, mode `read|write`, files, задач не больше 6. Инструмент есть только у основного агента с `--subagents`, у субагентов его нет. Грамматика по схеме держит и массив задач.
  - **Субагент — агент со своим разговором.** Системный промпт обычный, с одной строкой: основной агент видит только его финальный ответ, так что это отчёт. Дальше контекст проекта, а задача — его сообщение пользователя. Не больше 40 шагов, лимит времени — то, что осталось у хода. Модель та же, у gpt-oss на medium. Каждый шаг ждёт очереди к слотам сервера за основным агентом (§4).
  - **Изоляция записи.** Read-задача не получает инструментов, которые меняют файлы. Правка write-задачи вне её файлов — ошибка, о которой модели сказано, что о лишнем надо сообщить в отчёте. Write-задачи с общим файлом идут друг за другом (блокировки по файлам в порядке путей), остальные — одновременно.
  - **Подтверждения.** Субагенты спрашивают через approver сессии по одному, и вопрос называет задачу. Inbox появится с GUI.
  - **Итог становится сессией основного агента.** Изменённое и запущенное субагентом вливается в журнал правок основного агента (для `/changes` и `/revert`) и в журнал проверок (для статуса ответа).
  - **Отчёт приходит как tool result.** По каждой задаче: чем кончилась, сколько шагов, ответ (до 6000 знаков, со статусом проверки), изменённые файлы, сборки и тесты. Разговор субагента хранится сессией вида `subagent` в той же базе. Журнал основной сессии называет её (`subagent_session`), ATIF — у шага с `delegate`, а `t2` пишет трейсы субагентов рядом с основным.
  - **Показ.** `chat` выводит каждый вызов субагента одной строкой с номером задачи, когда вызов закончен: строки параллельных агентов перемешиваются. `run` пишет их в stderr.
  - **Сценарии.** Категория T2 `parallel`: три медленных набора тестов (`parallel-test-suites`), три модуля с ошибкой в каждом (`parallel-review-modules`) и контроль, где один поиск находит всё (`parallel-ports`).
  - **Замер 2026-11-03 (§11).**
    - Сама gpt-oss не делегирует ни разу, и со строкой в системном промпте о том, когда делегировать, тоже. Строка убрана.
    - Когда просит пользователь, параллельная часть идёт в 2,3 раза быстрее, но ход целиком почти не короче: шаг основного агента с `delegate` стоит 9–17 с.
    - Короткие задачи с субагентами в 3–5 раз дольше.
    - Поэтому `--subagents` выключен по умолчанию.
  - **Read-задача в проверке ответа.** Из журнала read-задачи в журнал хода берутся только сборки и тесты, запущенные или отказанные. Её команды с побочными эффектами остаются в журнале правок, чтобы их можно было просмотреть, но ответ из-за них больше не возвращается на сборку. Так было 2026-11-03: анализ в четырёх read-задачах отправил агента пользователя искать тесты после `python - <<'PY'` и `compileall`.

## 8. Подтверждения и чекпоинты

- **Без песочницы эта политика и есть граница безопасности** (ревью безопасности M0, `docs/research/2026-10-29/review-skeleton/`). Поэтому:
  - **Правки по пути.** Без вопроса применяются только правки внутри проекта, причём путь проверяется после разрешения симлинков. Правки вне проекта и защищённых путей всегда спрашиваются (`ognivo_core::approval::decide_edit`). Защищены: `.git/**`, `.gitattributes`, `.gitmodules`, `.claude/**`, `.mcp.json`, `.ognivo/**`, AGENTS.md, CLAUDE.md, `.vscode/**`, `.idea/**`, `.devcontainer/**`, `.envrc`, mise/asdf, `.cargo/**`, rust-toolchain, `.npmrc`, `.yarnrc*`, `.pnpmfile.cjs`, Makefile, `.github/workflows/**` и shell rc. В `pyproject.toml` защищены только таблицы `[tool.*]` (настройки pytest, hatch и т.п.), правки остальных секций идут без вопроса; если TOML не разбирается, правка тоже спрашивается. Все эти файлы заставляют git, CI, агента, редактор, сборку или shell запускать программы.
  - **Белые списки.** Команда считается «только чтение» или «проектный код», только если каждый флаг есть в её белом списке, а каждый путь разрешается (с симлинками) внутрь проекта. Рабочая папка тоже должна быть внутри проекта. У `cat`/`head`/`tail` аргументы — только обычные файлы. Отсюда:
    - `go run mod@latest`, `--manifest-path /…`, `make -C /`, `--prefix ../…`, `clippy --fix` спрашиваются;
    - `tail -f`, `rg -L/--pre/-z/--hostname-bin`, `grep -R`, `find -L` тоже спрашиваются.
  - **git — только в герметичном виде.** Исполнитель запускает git как `git -c core.fsmonitor=false --no-pager …`, а для diff/log/show добавляет `--no-ext-diff --no-textconv`. Флаги `--ext-diff`, `--textconv`, `--show-signature`, `--no-index` и `--output` спрашиваются.
  - **Сеть.** У WebFetch и любого MCP-инструмента эффект Network, поэтому они спрашивают. Аннотациям MCP (`readOnlyHint`) не доверяем.
- **Классификатор команд** (`ognivo_tools::classify_command`, M1) разбирает строку tree-sitter-bash:
  - составная команда разрешена, только если разрешена каждая её часть; решает худшая часть;
  - разбираются обёртки (`timeout`, `env`, `bash -c` и т.п.);
  - при ERROR-узлах — вопрос пользователю.
  - M1: `simple_commands` даёт простые команды из `&&`, `||`, `;`, переводов строки, пайпов (`|`, `|&`) и `!` с кавычками и экранированием, снятыми как в shell. Подстановки, раскрытие переменных, подоболочки и `{ }`, управляющие конструкции, функции, here-документы, фоновые задачи (`&`) и продолжение строки через `\` дают вопрос. Часть с присваиванием переменных, перенаправлением в файл (кроме `/dev/null` и `2>&1`-подобных) или словом, которое shell раскроет (glob, `{a,b}`, `~`), — тоже.
  - `cd` внутрь проекта прослеживается по потоку управления: после `&&` команда идёт из нового каталога, после `||` — из старого, после `;` — из любого, а части пайпа и скрипт `bash -c` своих каталогов не меняют. Пути проверяются из каждого каталога, где команда может оказаться, поэтому `cd src && cat lib.rs` идёт без вопроса, а `cd src || true; cat lib.rs` спрашивает.
  - Обёртки: `timeout [опции] СРОК`, `nice [-n N]`, `time`, `env` без настроек, `bash -c`/`sh -c` (скрипт классифицируется так же, вложенность не глубже 3). `echo`, `true`, `false` только печатают. Для пайпов в белый список добавлены `sort`, `uniq`, `cut`: `cargo test 2>&1 | tail -n 20` — это «проектный код» и при чистой рабочей копии идёт без вопроса.
  - Короткие флаги утилит с разбором getopt можно писать вместе (`ls -ltrA`, `grep -rn`, `cat -An`), если в белом списке каждая буква. Последней может стоять опция со значением, значение приклеено или идёт следующим словом (`od -An -tx1`, `grep -rnA3`). Длинная опция со значением пишется и через `=` (`--exclude-dir=.git`, `--max-count=5`). Без вопроса идут и дампы `hexdump`, `od` и `xxd` (у `xxd` — один файл: второй он перезаписывает).
  - `sed` без вопроса, если сценарий только печатает: адреса строк, `$` и `/regex/`, команды, которые не пишут файлов, не читают их и ничего не запускают (`p`, `d`, `s` с флагами `g`, `p`, `i`, `m` и числом, `y`, метки и переходы), а файлы — обычные файлы внутри проекта. Вопрос дают `-i`, сценарий из файла, команды `w`, `W`, `r`, `R`, `e`, флаги `s///w` и `s///e` и всё, чего разбор не знает. Разделитель `s` — только ASCII-пунктуация, чтобы сценарий делился одинаково и в байтовой локали. Ночь T2 2026-11-02: модели просили `sed -n '3137p' data/log.txt` и `find src -type f | sed 's|^\./||'` и получали отказ.
  - Скрипт проекта — `bash x.sh`, `sh x.sh`, `python3 x.py` (также `node`, `ruby`, `perl`), `./x.sh` или `scripts/x.sh` — это «проектный код», если скрипт — обычный файл внутри корня, а аргументы, кроме опций, указывают внутрь проекта. `python3 -m pytest` разбирается как `pytest`. Опции интерпретатору (`bash -x`), `python3 -c`, `-m` других модулей и скрипт со стандартного ввода дают вопрос. Пробелы нашлись на T2-mini: gpt-oss просил `ls -A`, `cat -A`, `hexdump -C` и `bash scripts/build.sh` и получал отказ.
  - Тот же разбор используют правила (§8, «Правила»): слова частей, присваивания и перенаправления.
- **Правила** (deny > ask > allow) — из `~/.ognivo/config.toml`, проекта и `.claude/settings.json` (`permissions`, например `Bash(cargo test:*)`). Опасные команды подсвечиваются.
  - M1 (`ognivo_core::rules`). Источники — пользователя: `~/.ognivo/config.toml` (таблица `[permissions]` со списками `allow`, `ask`, `deny`) и `~/.claude/settings.json` (или из `CLAUDE_CONFIG_DIR`); проекта: `.ognivo/config.toml`, `.claude/settings.json`, `.claude/settings.local.json`. Синтаксис правил — как в Claude Code.
  - Deny и ask действуют откуда бы ни пришли. Allow-правила проекта начинают действовать, только когда пользователь доверился ровно этому их набору: `chat` один раз спрашивает, правило «любая команда» выделено, ответ хранится в хранилище сессий и спрашивается снова, когда набор меняется. `run` берёт их, только если в `chat` ответили «да». Иначе клонированный репозиторий мог бы сам разрешить себе команды.
  - `Bash(cmd)` — ровно эта команда, `Bash(cmd:*)` и `Bash(cmd *)` — она и любые слова после (только целыми словами), `Bash` — любая. Составная команда (`&&`, `||`, `;`, `|`) разрешается правилами, только если каждая часть разрешена правилом или только читает. Часть с присваиванием переменных или перенаправлением в файл, как и команда, которую разбор не принимает (подстановки, подоболочки, управляющие конструкции), правилами слов не разрешается никогда. Deny и ask срабатывают на любой части, а у неразобранной команды — на её грубо нарезанных кусках.
  - `Read(path)` действует на read, grep и glob, `Edit(path)` — на edit и write. Путь — glob: `//abs`, `~/дом`, `/в-корне` и `в-корне`; `**` переходит каталоги, путь без шаблонов покрывает и то, что под ним. Файлы, закрытые deny или ask, не попадают в результаты grep и glob (результат говорит, сколько пропущено). Закрытое для чтения закрыто и для правки: результат правки показывает строки. Allow снимает вопрос о чтении вне проекта, но не о правке: правки вне проекта и защищённых путей спрашиваются всегда.
  - Аргументы команды проверяются как пути по deny и ask путей: от её cwd, `~/…` от домашнего каталога, у `--opt=путь` — значение. `cat .env` упирается в `Read(./.env)`, `cat ~/.ssh/id_rsa` — в `Read(~/.ssh/**)`. Пути, которые строит сам shell (glob, `grep -r .`), не видны; команде, которая не должна запускаться никогда, нужно своё Bash-правило.
  - Deny отказывает без вопроса и называет правило и файл. Правила для инструментов, которых в ognivo пока нет (WebFetch, `mcp__…`), сохраняются на будущее, а нечитаемое правило или файл показываются строкой «not a rule».
- **Режимы треда** (2026-11-10, по просьбе владельца; `ognivo_core::approval::Mode`). Режим делает политику строже или мягче до правил. Правила он не обходит: их ask и deny действуют в любом режиме. Правка защищённого пути или вне проекта ни в одном режиме не проходит без вопроса.
  - **Manual.** Спрашивается каждая правка и каждая команда, которая делает больше, чем читает (`cargo test` — и при чистой рабочей копии). Причина в вопросе: «manual mode: …».
  - **Edit automatically** (по умолчанию). Политика как есть: правки внутри проекта применяются сразу и ждут просмотра в Changes, команды спрашивают, как описано ниже.
  - **Plan.** Агент читает, ищет и выполняет команды, которые только читают. Правки, запись, патчи, команды с эффектами, задачи субагентов на запись и `!`-команды навыков отклоняются без вопроса, с объяснением модели. MCP спрашивает, как обычно.
    - В начале каждого хода в этом режиме и при переключении в него модель получает заметку: сначала план, ничего не менять, ответить планом (шаги, файлы, как проверить).
    - После выхода из режима модель получает заметку, что менять снова можно.
    - Тред, ответивший в режиме Plan, предлагает в GUI исполнить план в выбранном режиме (§10).
  - **Auto.** Без вопроса идёт то, что спросило бы: чтение вне проекта, команды с эффектами, сеть, проектный код при непросмотренных изменениях, MCP без правил. Спрашивают только правки защищённых путей и вне проекта и правила ask. Это выбор пользователя, который сидит перед окном. Безголовый `ognivo run` по-прежнему решает флагом `--approve` (`auto` — только в контейнере).
  - Режим один на тред и его субагентов (`ModeSwitch`). Агент читает его при каждом вызове, поэтому переключение действует и в идущем ходе. В `chat` режим меняет команда `/mode manual|edit|plan|auto`.
- **Правки применяются сразу** (решение 12). Журнал правок хранит pre/post-образы каждого файла (blake3 + zstd), это даёт точный откат по файлу и по hunk.
  - В конце хода вкладка Changes: дифф хода и сессии, accept/revert по файлу и по hunk, комментарии к строкам уходят в контекст следующего хода, commit.
  - Restore: код / диалог / оба / форк.
  - M1: для каждого файла журнал хранит байты до первой непросмотренной правки агента и байты его последней записи. В `chat` есть `/changes` (дифф сессии по файлам), `/accept` и `/revert` — для всего сразу или для одного файла. Revert возвращает файл; созданный агентом файл удаляет вместе с пустыми каталогами, созданными под него, а модель узнаёт об откате со следующим сообщением. Если файл менялся не только правками агента (командой или вручную), revert сначала спрашивает. Файл, вернувшийся к исходному виду (например, после `git checkout`), считается просмотренным. Журнал сохраняется в хранилище сессий (§11) после каждого вызова, который его изменил, содержимое файлов — блобами blake3 + zstd. Поэтому `chat --resume` откатывает и то, что поменял прошлый запуск ognivo, даже если тот упал. Откат по hunk появится позже.
  - Побочные эффекты shell-команд в журнал не попадают. Диалог подтверждения предупреждает о необратимом. Теневые git-снапшоты не делаем: Codex убрал свои из-за проблем.
- **Класс «исполняет код проекта».** Это `cargo test/build/run`, `npm test/run`, `pytest`, `make`, `go test` и т.п. Такие команды запускаются автоматически, только если в рабочей копии нет непросмотренных изменений (`WorkspaceState`). Иначе нужно подтверждение, ведь правки применяются без вопроса. Без этого правила агент мог бы исполнить любой код, записав его в тест или `build.rs`.
  - Рабочая копия становится «грязной» при первом изменении от любого агента или субагента: правки, запись, одобренные команды с побочными эффектами, вызовы MCP.
  - Чистой она становится только после Accept или Revert во вкладке Changes. Каждый ход состояние не сбрасывается и хранится вместе с сессией.
  - При возобновлении сессии непросмотренными считаются и те изменения из `git status`, которых нет в её журнале: их сделал не ognivo.
  - В диалоге подтверждения показывается список непросмотренных файлов.
- **Песочница** (bwrap + seccomp, сеть off/on) — после v1, как опциональный режим «автозапуск в песочнице».

## 9. Терминал, MCP, совместимость с Claude Code

### Терминал

- **По умолчанию команда идёт без TTY:** pipes, `stdin=/dev/null`, `setsid`. Окружение: `PAGER=cat`, `GIT_PAGER=cat`, `GIT_TERMINAL_PROMPT=0`, `LC_ALL=C.UTF-8`, `NO_COLOR=1`, `AI_AGENT=ognivo`. `CI=1` глобально не ставим.
- **cwd сохраняется** между командами. Сохранение env через EXIT-trap — позже.
- **yield, wait_for и таймауты.** Команда, упёршаяся в таймаут, не убивается, а уходит в фон. Для фоновых сервисов есть панель процессов.
- **Kill:** SIGINT → SIGTERM группе → SIGKILL. Командам ставится `oom_score_adj=+500`, чтобы сборка не убила llama-server.
- **Окружение дочерних процессов.**
  - Без `*_API_KEY`, `*_TOKEN` и `OGNIVO_API_KEY`.
  - rg запускается с `--no-config`, без `RIPGREP_CONFIG_PATH`.
  - Команды класса «только чтение» получают жёсткий лимит времени и вывода. По лимиту их убивают, а не уводят в фон.
  - Полный лог ограничен, например, 64 МиБ: голова плюс хвост.
  - В начале каждого хода cwd сбрасывается в корень проекта.
- **Бюджет вывода — в токенах модели.** Голова 30% + хвост 70%, полный лог пишется в файл с путём, ANSI и перерисовки схлопывает VT-эмулятор. Envelope под модель:
  - gpt-oss — raw text по образцу harmonyagent;
  - Gemma — `response:bash{exit_code,output,truncated}`.
- **PTY-сессии** (M5, `pty-process`):
  - интерактив и TUI;
  - headless VT (`vt100` / `avt`) даёт модели снапшот экрана;
  - `write_stdin` / poll с минимальной паузой;
  - GUI показывает тот же поток в xterm.js, пользователь может перехватить управление.

### MCP

- **Клиент** на `rmcp` 3.x через `serve_with_lifecycle(ClientLifecycleMode::Auto)`. Поддерживаются обе эпохи: stateless 2026-07-28 и legacy initialize. Эпоха кешируется на сервер.
- **Транспорты:** stdio и Streamable HTTP. Устаревший HTTP+SSE rmcp не поддерживает.
- **OAuth 2.1:** PKCE, системный браузер + loopback redirect. Токены — в файле 0600 (сделано так, M3; Secret Service отложен, см. «Вход на удалённые серверы» ниже). CIMD по спецификации 2026-07-28 требует публичный HTTPS-документ (GitHub Pages после публикации), до этого — DCR там, где сервер его поддерживает.
- **Конфиги:** `.mcp.json` в проекте и `~/.ognivo/mcp.json`. Серверы из проекта запускаются только после доверия к workspace; точная команда показывается до запуска.
- **Tool gateway:**
  - имена `srv__tool` по шаблону `[a-z0-9_]` с обратной картой;
  - нормализация схем под диалект модели;
  - валидация аргументов;
  - капы вывода с хэндлами;
  - пиннинг хеша определений.
- **tool_search** возвращает декларации **в нативном синтаксисе модели**, дальше модель вызывает инструмент напрямую. Грамматика запроса расширяется, массив tools не меняется, KV не ломается. `mcp_call` остаётся фолбэком. Сделано так, M3, 2026-11-05 — см. «Много инструментов» ниже.
- M3, начат 2026-11-05 (крейт `ognivo-mcp`, rmcp 3.7.0 — последний выпуск не моложе двух недель).
  - **Конфиги** — формат `mcpServers` (и `servers`, как у VS Code):
    - сначала локальные серверы Claude Code для проекта из `~/.claude.json`;
    - затем `.mcp.json` проекта;
    - затем `~/.ognivo/mcp.json`;
    - затем пользовательские серверы Claude Code из `~/.claude.json` (при `CLAUDE_CONFIG_DIR` — оттуда).

    Имя из двух мест берётся из первого. `${VAR}` и `${VAR:-default}` раскрываются в команде, аргументах, окружении, URL и заголовках. `disabled: true` выключает сервер, а HTTP+SSE — понятная ошибка: rmcp его не поддерживает.
  - **Доверие.** Серверы `.mcp.json` запускают команды проекта, поэтому стартуют только после доверия ровно к ним: ключ — их конфиги целиком, другая команда — новый вопрос.
    - `chat` перед стартом показывает точные команды и спрашивает y/n.
    - Ядро спрашивает GUI запросом `mcp/trust`, и GUI показывает диалог с командами.
    - `run` запускает их, только если доверие уже дано.
  - **Транспорты** — stdio и Streamable HTTP с заголовками из конфига (`Authorization` туда же). Оба работают в режиме Auto: сначала `server/discover`, при «нет метода» — откат на `initialize`.
  - **Процессы.** stdio-сервер запускается в своей группе процессов, stderr уходит в никуда. Когда шлюз закрывается, он убивает группы сразу, поэтому `npx` уходит вместе со своим node даже при выходе ognivo. Серверы стартуют одновременно, каждому даётся 60 с; кто не стартовал, назван с причиной.
  - **Имена и объявления.** Инструмент называется как у Claude Code, `mcp__<server>__<tool>`: всё, кроме букв, цифр и `_`, становится `_`, длина до 64, повтор получает номер. Объявления идут после инструментов ognivo в порядке имён, поэтому префикс промпта не меняется. К описанию добавлено «(MCP server X)», схема берётся как есть: построитель грамматики незнакомую схему делает «любым JSON» (§5.7).
  - **Вызов.**
    - Агент сам разбирает вызов MCP раньше проекции, схему проверяет сервер.
    - Право даёт правило Claude Code: `mcp__server` и `mcp__server__*` — все инструменты сервера, `mcp__server__tool` — один. Без правила задаётся вопрос.
    - Действие вопроса — «сервер · инструмент», поэтому «на сессию» разрешает весь инструмент. Аргументы видны в причине.
    - Время — 120 с, но не больше остатка лимита хода.
  - **Результат** — текст для модели:
    - первая строка `[mcp: server · tool]` или `[error] … failed:`;
    - текст содержимого как есть, картинка или звук названы, ссылки и ресурсы показаны;
    - структурный ответ отдаётся, когда другого нет;
    - не больше 24 000 знаков.
  - **Где ещё MCP.**
    - В модели событий это новый вариант вызова `Mcp {server, tool, arguments}`, только добавление.
    - `chat` показывает строку «→ mcp server · tool аргументы».
    - GUI — карточку MCP с аргументами и ответом.
    - `ognivo mcp` показывает серверы проекта, откуда они, стартуют ли и какие у них инструменты.
    - Субагентам MCP пока не даётся: задача на чтение ничего не меняет, а инструмент MCP может.
  - **Проверено:**
    - юнит-тесты конфигов, имён, результатов и правил;
    - сервер эпохи `initialize` на Python по stdio и по Streamable HTTP с токеном (без токена — отказ);
    - `run` с сервером пользователя: инструменты в запросе после ognivo, вызов по правилу, отказ без правила, ожидание доверия для серверов проекта;
    - Playwright в настоящем окне: диалог доверия, вопрос в треде, ответ сервера в карточке.
  - **Много инструментов** (`ognivo_mcp::Listing`, `--mcp-tools auto|declare|search`).
    - По умолчанию (`auto`) инструменты объявляются, пока их не больше 40 и объявления занимают не больше 24 000 знаков (около 6K токенов, десятая часть контекста в 64K). Иначе вместо них модель получает два инструмента:
      - `tool_search(query)`: несколько слов о том, что инструмент должен делать, или `select:` и имена через запятую;
      - `mcp_call(tool, arguments)`: имена всех инструментов — варианты `tool`, поэтому модель знает, что есть, и не вызовет того, чего нет.
    - Массив tools один на всю сессию, что бы ни нашёл поиск: префикс промпта и кеш сервера держатся.
    - **Поиск** (`ognivo_mcp::search`) — по словам, без модели. Слово запроса ищется без учёта регистра, `snake_case` и `camelCase` делятся на слова, множественное число и `-ing` сводятся к основе. Очки: 4 за слово в имени инструмента, 2 — в имени сервера, 1 — в описании, 1 — в именах параметров. Инструменты с очками меньше трети лучшего отсекаются, чтобы слово одного описания не тянуло соседей к инструменту, у которого слова в имени. Отдаётся не больше пяти; запрос, равный имени инструмента, находит его одного.
    - **Результат** — объявления найденного так, как модель видит их в своём промпте: у gpt-oss — TypeScript в `namespace functions`, у Qwen — блок `<tools>` с JSON. У Gemma объявления пишутся управляющими токенами, поэтому она получает строки JSON (`ognivo_models::declarations`). Затем строка о том, как вызвать:
      - на Native-пути — по имени, как любой инструмент. Драйвер получает все инструменты MCP в `StepRequest::callable`: грамматика и читатель берут их вместе с объявленными, а промпт — нет;
      - на Generic-пути — через `mcp_call`: грамматику там строит сервер, и она знает только массив tools.
    - Когда ничего не подошло, результат называет все инструменты. Вызов через `mcp_call` разбирается в вызов самого инструмента: правила, вопрос «сервер · инструмент», событие `Mcp` и карточка GUI — те же. Поиск — новый вариант вызова `ToolSearch {query}` (только добавление), GUI показывает его карточкой «Find».
    - Описание `tool_search` содержит каталог: имя каждого инструмента и первое предложение его описания (до 100 знаков), пока каталог не длиннее 8000 знаков; дальше — одни имена. Без каталога gpt-oss выбирал среди 40 инструментов по имени, а искал только выбранный: `get_exchange_rate` вместо `convert_currency`, `search_issues` вместо `create_issue`.
    - Аргументы `mcp_call` грамматика не держит по схеме инструмента, поэтому их проверяет агент: обязательные на месте, лишних нет, где схема их запрещает. Вызов, который не подходит, получает назад объявление инструмента. gpt-oss звал `create_issue`, не поискав, с `repository` вместо `repo`.
    - Сообщение о проекте (§5.6) называет серверы MCP и говорит, что их инструменты выходят за проект: вопрос о том, что они покрывают, требует вызова, а не ответа по памяти и не поиска в проекте. Строка системного промпта «вопрос, которому не нужно ничего из проекта, — без инструментов» толкала gpt-oss отвечать о курсе валют по памяти, а «нашу внутреннюю документацию» он искал Grep'ом в пустом проекте.
    - **Замер.** В T2 добавлена категория `mcp`: пять задач (завести issue с меткой, погода сейчас, перевод валюты, поиск по внутренней документации, сообщение в канал) на сервере `evals/t2/mcp/workspace.py`. Задача гонится при 5, 15 и 40 инструментах: первые пять — нужные, следующие десять — их ближайшие соседи (`list_issues` рядом с `create_issue`, `get_forecast` рядом с `get_weather`), остальные — прочие инструменты рабочего пространства. `tool_correct` — доля прогонов, где первый вызов MCP — нужный инструмент. Порог M3 — не меньше 90% при 5, 15 и 40.
    - Первый замер, 2026-11-05: коммит 5b48f3f, seed 1–3, Generic-путь, по 45 прогонов на модель и режим (`ID+mcp-declare`, `ID+mcp-search`), 28 мин GPU. `tool_correct` при 5, 15 и 40 инструментах:

      |---|---|---|---|---|---|

      | gpt-oss-20b | поиск | 10/15 | 11/15 | 8/15 | 28/45 |

    - Причины, по убыванию.
      - gpt-oss в 11 прогонах из 45 в режиме поиска и в 6 из 45 с объявленными не позвал MCP вовсе. Курс валют он называл по памяти, а «внутреннюю документацию» искал в пустом проекте и выдумывал команду.

    - Правки после замера — каталог, проверка аргументов `mcp_call` и строка о серверах в сообщении о проекте (выше). Второй замер, тот же день, коммит e40c4e3, 21 мин GPU:

    - Объявленные инструменты при 15 и 40 ни у одной модели не хуже поиска и экономят шаг. Поэтому `auto` объявляет до 40 инструментов (столько проверено), а не до 20. С этой границей порог M3 взят: при 5, 15 и 40 у gpt-oss 100, 100 и 93%, у Qwen 100, 100 и 100%, у Gemma 100, 93 и 100%. Поиск остаётся для серверов больше 40 инструментов или 24 000 знаков объявлений; там он даёт 87–98%.
  - **Вход на удалённые серверы (OAuth)** — `ognivo_mcp::oauth`, M3, 2026-11-05. Клиент OAuth взят из rmcp (функция `auth`, ещё 19 крейтов, все старше двух недель).
    - Сервер, ответивший при старте 401 с `WWW-Authenticate`, не стартует: «it wants you to sign in: ognivo mcp login NAME». `chat` сразу спрашивает, войти ли сейчас, и после входа запускает серверы заново. Ядро спрашивает GUI запросом `mcp/sign_in`: GUI показывает диалог «Sign in / Not now», а на «Sign in» ядро открывает браузер и стартует тред, когда браузер вернётся.
    - Вход — `ognivo mcp login NAME`: OAuth 2.1 с PKCE (S256), браузер пользователя (`$BROWSER`, иначе `xdg-open`) и возврат на loopback-порт `127.0.0.1` (RFC 8252). Ожидание — до 5 минут. Сервер авторизации находится по метаданным сервера (RFC 9728, RFC 8414).
    - Клиент — заданный в конфиге (`oauth`: `clientId`, `clientSecret`, `scopes`, `callbackPort`, как пишет Claude Code), иначе он регистрируется динамически (RFC 7591). CIMD требует публичной HTTPS-страницы ognivo, её пока нет.
    - Токены лежат в `~/.ognivo/mcp-auth/<имя>.json` с правами 0600 в каталоге 0700, вместе с URL сервера. Файл другого URL не используется: имя, отданное в конфиге другому серверу, токен не получает. Secret Service отложен: D-Bus есть не везде (SSH, контейнеры), а зависимости тяжёлые. Claude Code на Linux тоже держит токены в файле 0600.
    - Сессия берёт токен из файла и обновляет его, когда до конца остаётся меньше 30 с. Обновления из разных процессов ognivo идут по одному (`flock` рядом с файлом), поэтому одноразовый refresh-токен не тратится дважды. Отвергнутое обновление требует нового входа.
    - `ognivo mcp logout NAME` забывает вход; `ognivo mcp` пишет у сервера «signed in».
    - `ognivo mcp call NAME TOOL [JSON]` запускает один сервер и вызывает его инструмент через тот же шлюз, что у сессии, со временем старта и ответа: так проверяется, отвечает ли сервер. 2026-11-06 так проверен Context7 владельца: старт 0,4 с, `resolve-library-id` 1,6 с, `query-docs` 1,8 с. Его «зависание» в ручной проверке было без рукопожатия MCP: до `initialize` сервер на `tools/call` не отвечает.
    - Проверено на тестовом сервере на Python, который и MCP за OAuth, и свой сервер авторизации (метаданные, DCR, PKCE, одноразовые refresh-токены). Проверены запрос входа, вход, права файла, использование токена, обновление с заменой refresh-токена, выход. `ognivo mcp login` и вход через ядро (`mcp/sign_in`) проверены с `$BROWSER`, который идёт по редиректу.
  - **Инструкции серверов** (`instructions` ответа `initialize` или `server/discover`) идут в сообщение о проекте после строки о серверах: «The MCP server X says how to use it: …», до 2000 знаков с каждого. Так их даёт и Claude Code. Это недоверенный ввод, как описания инструментов: на Generic-пути его разрывает страж, на Native-пути он режется (§5.3). `ognivo mcp` показывает их первую строку.
  - **Промпты серверов** (`prompts/list` и `prompts/get`, M3, 2026-11-06). Решение владельца: модель должна знать, что промпты есть и как ими пользоваться, а не только пользователь, как в Claude Code.
    - Промпт называется как инструмент: `mcp__<server>__<prompt>`. Сервер без промптов или с ошибкой в их списке работает с одними инструментами.
    - Сообщение о проекте перечисляет промпты после skills: имя, сервер, описание и аргументы, отмечая обязательные. Там же сказано, как их грузить.
    - Модель грузит промпт инструментом skill. Аргументы идут во второй ключ (`args`, `arguments` или `task`) JSON-объектом или значениями по порядку: shell-слова, один аргумент берёт весь текст, лишние слова уходят в последний. Без обязательного аргумента — ошибка со списком аргументов.
    - Аргументы уходят серверу, поэтому загрузка от модели проходит правила MCP: правило `mcp__server` её пускает, без правила задаётся вопрос, правило deny отказывает.
    - Пользователь запускает промпт как `/mcp__server__prompt значения` в `chat`, `run` и GUI, без вопроса: это его команда. Модель получает строку и текст промпта; сообщения ассистента помечены `[assistant]`.
    - `chat /help` и `ognivo mcp` показывают промпты с аргументами.
    - Проверено на тестовом сервере (`echo.py`, промпт с обязательным аргументом): список, текст, ошибка без аргумента, загрузка моделью, `/команда` пользователя и ход, который не начинается.
  - **Чего ещё нет:**
    - ресурсы, `list_changed`, кеш эпохи сервера (молчащий сервер старой эпохи ждёт 10 с).

Потом идут файлы каждого каталога от корня ФС до корня проекта: AGENTS.md, CLAUDE.md, `.claude/CLAUDE.md`, CLAUDE.local.md. Всё это попадает в первое сообщение разговора, за путём проекта (§5.6), от общего к частному, и модели сказано, что более поздний файл побеждает, а слова пользователя — все файлы. Файлы подкаталогов проекта приходят вместе с результатом первого вызова, который читает или меняет файл под ними, и действуют только в своём поддереве.

Файлы пользователя и каталогов над проектом могут указывать куда угодно, поэтому учитываются, только если ими и ссылкой на них владеет пользователь или root: писать в `/tmp` может любой.
  - Каждый файл попадает в разговор один раз: симлинк, повторный импорт, копия или файл из одних импортов ничего не добавляют. Одна загрузка занимает не больше 32 KiB (столько по умолчанию у Codex): место сначала получают ближайшие к работе файлы, обрезанный файл помечен. `/clear` перечитывает файлы. Что модель получила и что пропущено (с причиной), `chat` и `run` показывают, а в JSONL это событие `instructions`. `AGENTS.override.md` из Codex и `.claude/rules` пока не читаются.

  - Хуки проекта — это его команды, поэтому они выполняются только после доверия к ровно этому набору, как серверы `.mcp.json`. `chat` спрашивает, GUI получает запрос `hooks/trust`, `run` берёт ответ, данный в `chat`.

    - Stop и SubagentStop;

    - SessionEnd;
    - PreCompact (auto);
    - Notification (permission_prompt).
  - Matcher из букв, цифр, `_`, `-`, пробелов, `,` и `|` — точные имена, любой другой — регулярное выражение. Условие `if` поддержано только в форме `Bash(…)`.

    - общие поля: `session_id`, `transcript_path` (пустой: такого файла у ognivo нет), `cwd`, `permission_mode` `default`, `hook_event_name`, и поля события;

    - `tool_response` — подмножество форм Claude Code.

    - вызов — модель получает отказ;
    - промпт — ход не начинается;
    - Stop — модель возвращается к работе, до 8 раз подряд;

  - Другие коды — заметка пользователю, а действие идёт дальше.
  - `permissionDecision`:
    - `allow` снимает вопрос, но не отказ правила и не вопрос о правке: правки вне проекта и защищённых путей спрашивают всегда (§8);

Сессия сохраняется по ходу работы (§11): `--resume ID` или `--continue` (последняя сессия `chat` этого проекта) продолжает её с тем же разговором, журналом правок, профилем, уровнем рассуждения и seed. Ход, на котором ognivo остановился, закрывается так же, как прерванный. Разрешения `a` после возобновления спрашиваются заново. Сессия без ходов при выходе удаляется, а у сохранённой при выходе показано, как её продолжить. `ognivo sessions` перечисляет сессии проекта, с `--all` — всех проектов, с `--search` — те, в чьих сообщениях и ответах есть все слова. Когда контекст заполняется, история сжимается посреди хода (§5.6): `· compacting the conversation: about 70.1K tokens, over the 68.8K budget`, затем `· compacted: 23 messages became a summary of 310 words; 2 steps kept`. `/clear` начинает следующий разговор той же сессии, а непросмотренные изменения остаются непросмотренными. Между ходами `/changes`, `/accept` и `/revert` работают с журналом правок (§8). Строка под ходом перечисляет непросмотренное, а вопрос перед сборкой или тестами показывает, что именно не просмотрено. Файлы инструкций (§9) перечислены под баннером, а файлы подкаталогов — строкой `· instructions: …` после вызова, с которым они пришли. Там же файлы правил (§8) с числом правил в каждом и вопрос о доверии к allow-правилам проекта.

## 11. Хранилище, трейсы, eval

- **Хранилище:**
  - `~/.ognivo/`: `config.toml`, `mcp.json`, пользовательские override профилей;
  - данные — `~/.ognivo/data/`: SQLite (rusqlite) с append-only event log (`seq`), колонкой сырых ID токенов (nullable с M1 — без миграции на Native), FTS5 для поиска по транскриптам; блобы журнала правок.
  - M1 (`ognivo-store`, `ognivo_core::session`): файл `ognivo.db` с правами 0600, WAL, схема версии 1 в `user_version` (более новую схему старый ognivo не открывает). Сессия — это `chat` или `run`, привязанная к проекту, профилю, уровню рассуждения и seed. В ней разговоры (следующий начинают `/clear` и компакция) с сообщениями ровно в том виде, в каком их получила модель, и с путями, которые разговор прочитал или записал. Журнал событий — с глобальным `seq`. Там же сообщение пользователя, ответы на вопросы, конец каждого хода, начало каждого разговора с его системным промптом и контекстом проекта (после компакции и с её сообщением) и каждая генерация целиком: текст, рассуждение, вызовы (выполненные и отвергнутые), исход, seed, токены (обработанные, из кеша, сгенерированные), время и sha256 запроса (сообщений и инструментов). Поток текста и рассуждения отдельными событиями остаётся, только если генерация не закончилась. Журнал правок — файлы, каталоги и команды, содержимое лежит в `blobs` под хешем blake3, сжатое zstd; блоб, на который ничего не ссылается, удаляется. FTS5 ищет по сообщениям пользователя и ответам. Ядро сохраняет сессию после каждого результата вызова и каждой заметки, а журнал правок — сразу после каждой записи файла, так что после падения теряется самое большее текущий вызов, но не прежнее содержимое файла. Если хранилище отказало, сессия идёт дальше в памяти, а пользователь видит это один раз. Пути хранятся байтами, как их пишет ОС. Трейсы в формате ATIF строятся из этого журнала событий.
  - M4: схема версии 3 добавляет `wire` — то, что `ognivo core` сказал клиентам о своих тредах, по `seq` их потока (§3). Текстовые дельты не хранятся: элементы, из которых они сложились, хранятся целиком. Пишет таблицу только ядро (одно на каталог данных). Удаление сессии удаляет и её события, вместе с событиями её субагентов.

  - M1 (`ognivo_core::trace`): `ognivo sessions --atif ID` печатает траекторию сессии, `ognivo run --atif FILE` пишет её в конце прогона (это `trajectory.json` для Harbor). Модели Harbor запрещают необъявленные поля, поэтому всё своё лежит в `extra`.
  - Шаги: системный промпт разговора и контекст проекта — `system` (снова, только если поменялись), сообщение компакции и каждая заметка ognivo модели — тоже `system`; сообщения пользователя — `user`; каждая генерация — `agent` с текстом, рассуждением, выполненными вызовами и их результатами в `observation`, `llm_call_count: 1` и метриками (`prompt_tokens` включает взятые из кеша, `cached_tokens`, `completion_tokens`, в `metrics.extra` — время промпта и генерации). В `extra` шага: зачем генерация (`step` или `summary` компакции), исход (`calls`, `answer`, `truncated`, `malformed`, `repeating`), причина остановки, seed, sha256 запроса, отвергнутые вызовы, а также правки, вопросы с ответами и файлы инструкций её вызовов.
  - В корне: `agent` (ognivo, версия, профиль, объявления инструментов в форме OpenAI), `final_metrics` (суммы токенов и число шагов), `extra.ognivo` (сессия, проект, профиль, уровень, сервер, seed, исход каждого хода, счётчики). ID токенов на Generic-пути нет.

- задание e2e: окно на настоящем ядре против поддельного llama-server под xvfb, с `kernel.apparmor_restrict_unprivileged_userns=0` для песочницы Chromium.

Версии actions закреплены точными тегами не моложе двух недель. Перед этим `check.sh` прошёл на чистом клоне с пустым `HOME`: без git-идентичности, `~/.ognivo`, `~/.claude` и записей.

Итого ≈ 28–37 недель до v1. CLI на каждый день — неделя ~5–6. Native gpt-oss и субагенты — ~11. GUI на каждый день — ~15–18. Три модели и MCP — ~20–24. Факт на 2026-11-02: M0 и M1 до живых замеров заняли 4 дня. Дальше темп задают GPU-ночи и неделя живой работы через CLI.

## 14. Риски

- **Потолок моделей.** gpt-oss-20b слаб в терминальных задачах (TB2.1 ≈ 14%), Gemma 26B — на длинных (TB Hard 14, MRCR-128K 44). Qwen3.8-27B dense, а значит медленнее MoE. Харнесс должен давать структуру: план, проверки, Continue, детекторы.
- **Одна GPU 24 ГБ.** Одна модель на сервер; субагенты делят пропускную способность; ночное окно — всего 3 ч.
- **Неоднородные серверы.** ik_llama.cpp, старые сборки, чужие шаблоны — отсюда caps, доктор и деградированные режимы.
- **Темп llama.cpp** (~30 сборок в день) и дрейф шаблонов. Пины, golden-тесты, регрессионный гейт.
- **Утомление от подтверждений** и дыра «правки + `cargo test`» (§8).
- **Заморозка событий до M3.** GUI подключается к модели событий раньше, чем появятся MCP gateway и tool_search. Если они изменят форму item'ов, заморозку придётся ломать. Скорее всего этого не случится: MCP-инструменты идут через тот же ToolProjector с каноническими ID. Проверить это прототипом событий MCP до заморозки.
- **Дрейф форматов Claude Code** (хуки, settings) — совместимость только по подмножеству, проверяется фикстурами. MCP в переходе между эпохами, а OAuth CIMD требует хостинга.
- **Объём для одного человека.** Помогают критерии выхода, правило +30% и разделение работы: AI-агенты делают UI-кит, CLI, хранилище и MCP-клиент; владелец обязательно ревьюит допуски кодеков, KV-инварианты и движок разрешений.
